# Best Practices: создание нового проекта — стек и модели

> Обязательное приложение к [AGENTS.md](AGENTS.md). Читается при старте
> любого нового проекта (этапы Discovery/Design Golden Path) — **до** выбора
> стека и генерации кода. Правила ниже — не «варианты на выбор», а дефолт
> компании: отклонение возможно только по явному решению пользователя,
> зафиксированному в `NOTES.md` проекта.

---

## 1. Проектирование агента — SDD (Spec-Driven Development)

Любой агент (и мультиагентная система) сначала описывается спецификацией,
и только потом реализуется — см. AGENTS.md §3. Минимум, что фиксирует
спецификация агента до кода:

- назначение агента и критерии приёмки (из `intent.md`);
- схема входа/выхода — типизированные модели (pydantic), не «сырые строки»;
- инструменты (tools): список, контракт каждого, какие внешние системы трогает;
- для мультиагентных систем — схема агентов: кто кого вызывает, что
  передаётся между ними, где человек в контуре;
- границы автономии по AGENTS.md §5 (что агент делает сам, где спрашивает).

Спецификация лежит в репо (markdown/схема) и является входом для этапа
Prep. Код, не соответствующий спецификации, — это ошибка кода, а не повод
молча поправить спецификацию.

## 2. Фронтенд — React по темплейту компании

Фронтенд-проект и интерфейс **обязательно** создаются на React из
темплейта [`templates/frontend-next-14-starter/`](templates/frontend-next-14-starter/)
этого каталога. Не начинать фронт «с чистого листа» и не брать другой
фреймворк без явного решения пользователя.

Что в темплейте: Next.js 14 (pages router) + React 18, Tailwind CSS 4,
zustand (стейт), recharts (графики), headlessui/heroicons, sass, gsap,
готовый Dockerfile; структура `components/` (common/pages), `hooks/`,
`contexts/`, `utils/`, `constants/`, `styles/`.

Как использовать:

```bash
cp -r <каталог-скиллов>/templates/frontend-next-14-starter <проект>/frontend
cd <проект>/frontend
# заменить name в package.json на имя проекта
npm install
npm run dev
```

Правила поверх темплейта:

- структуру папок темплейта сохранять — компоненты в `components/`,
  хуки в `hooks/`, утилиты в `utils/`, не изобретать свою раскладку;
- версии базового стека (Next 14 / React 18 / Tailwind 4) не поднимать
  «заодно» — только осознанным решением с записью в `NOTES.md`;
- если проект ведётся по дизайн-конвенциям NeuroLab (shadcn) — применяется
  скилл `/nlab-design`, и он имеет приоритет по части UI-стека.

## 3. Агенты — pydantic-ai

Агентов и схему агентов делаем на **pydantic-ai** (Pydantic AI):

- документация: <https://ai.pydantic.dev/>;
- для агента, пишущего код: индекс всей доки в формате llms.txt —
  <https://ai.pydantic.dev/llms.txt> — загрузить и ходить по нужным
  страницам оттуда, а не писать API по памяти. Отдельного официального
  MCP-сервера с документацией у pydantic-ai нет (проверено 2026-07-26);
  llms.txt — штатный путь;
- схемы входа/выхода агентов — pydantic-модели (structured output),
  инструменты — типизированные tools; это напрямую стыкуется со
  спецификацией из п.1;
- мультиагентные связки (agent delegation, programmatic hand-off) — тоже
  средствами pydantic-ai, схема связки — в спецификации до кода;
- MCP-интеграции агента (клиент/сервер) — по разделу MCP документации
  pydantic-ai.

## 4. Git-репозиторий проекта и деплой — только выданный репозиторий

Проект живёт в GitHub-репозитории, который **создаётся централизованно**,
а не самим пользователем/агентом. Порядок:

1. Пользователь пишет одному из ответственных в Telegram —
   [@sanchezgl](https://t.me/sanchezgl) или
   [@KirillBorovkov](https://t.me/KirillBorovkov) — просит создать
   репозиторий под проект и **передаёт свой никнейм на GitHub** (чтобы ему
   выдали доступ).
2. Ответственный создаёт репозиторий и даёт доступ; пользователь получает
   URL репозитория.
3. Весь проект коммитится и пушится **именно в этот репозиторий** — с
   первого коммита и далее (append-only-аудит из AGENTS.md §7 работает
   только если история лежит в общем репо).

Правила для агента:

- нет выданного репозитория → **не создавать свой** (`gh repo create`,
  личные репо, «временные» ремоуты — нельзя); остановиться и попросить
  пользователя написать ответственным (шаг 1). До получения репозитория
  можно работать локально в git, но первый push — только в выданный;
- проверка перед push/деплоем: `git remote -v` указывает на выданный
  репозиторий; URL зафиксирован в `NOTES.md` проекта при получении;
- деплой (скилл `/dokploy`) тянет код из GitHub — значит, деплоится ровно
  то, что запушено в выданный репозиторий, из него же его видит
  GitHub-провайдер Dokploy-сервера.

## 5. Модели в Claude Code — кто что делает

Постоянная инструкция для Claude Code в проектах:

| Задача | Модель / исполнитель |
|---|---|
| Проектирование: архитектура, спецификации (SDD), декомпозиция, ревью решений | **Fable-5 или Opus-5** — основная сессия (`/model`) |
| Задачи кода и прочая исполнительская работа: реализация по спецификации, тесты, рутинные правки | **Sonnet-5** — субагенты (Agent tool с `model: "sonnet"`) |
| Контроль результата | основная сессия (Fable-5/Opus-5) **сама**: проверяет код субагентов — читает диффы, гоняет тесты/линтер, делает правки и доводит до рабочего состояния |

Правила:

- основная сессия не «сдаёт» работу субагента непроверенной: каждый
  результат Sonnet-5 проходит через ревью диффа + запуск проверок, итог
  фиксируется в `EVIDENCE.md` (проверяемо: какие тесты, какой результат);
- проектные решения (архитектура, схема агентов, выбор стека) субагентам
  не делегируются — их принимает основная сессия и фиксирует в
  спецификации;
- декомпозиция на субагентные задачи идёт по `feature-list.json`
  (AGENTS.md §6): одна подзадача — один субагент с чётким контрактом
  вход/выход.
