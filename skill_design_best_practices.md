# Best Practices: проектирование скиллов для ИИ-агентов

> Источник принципов: whitepaper "AI-Disrupt PDLC" (К. Меньшов, Сбер CIO).
> Документ адаптирует концепции SDD, Context Supply Chain, Policy as Code
> и Golden Path под задачу стандартизации скиллов для отделов.

---

## Зачем это нужно

Цель — чтобы **любой человек без глубокой технической экспертизы**, вооружённый
своим ИИ-агентом и набором скиллов, на выходе получал проект, который:

- собран по единой структуре (SDD/DDD),
- проходит через предсказуемый процесс (Discovery → Design → Prep → Deploy),
- оставляет проверяемый след (логи, git-коммиты, evidence-артефакты),
- готов к интеграции в общую систему без ручной доработки "переводчиком".

Ключевая идея документа: **среда важнее модели**. Скилл — это часть среды.
Если скилл нормально спроектирован, он работает одинаково хорошо с любой
моделью и с любым уровнем пользователя. Если скилл — просто "текст с советами",
результат зависит от того, кто его читает (человек или агент) и насколько
внимательно.

---

## Принцип 1. У каждого скилла есть метаданные, а не только текст

Скилл — версионируемый артефакт, а не разовая инструкция. Без метаданных
невозможно понять, актуален ли он, кто отвечает за обновление, и можно ли
на него полагаться.

Обязательные поля (frontmatter):

```yaml
owner:            # кто отвечает за скилл
version:          # semver
status:           # draft | review | published | in-use | deprecated
scope:            # на какие проекты/агентов распространяется
depends_on:       # какие скиллы должны отработать раньше (см. Принцип 3)
last_reviewed:    # дата последнего пересмотра
```

Правило: скилл в статусе `draft` не должен использоваться в проде. Пересмотр
скилла — не реже раза в квартал, иначе он "протухает" (устаревание — один
из ключевых рисков Context Supply Chain).

## Принцип 2. Разделяй Guidance и Enforcement

Это центральное различие документа (Policy as Code):

| | Context-as-guidance | Policy enforcement |
|---|---|---|
| Что это | Рекомендации в теле скилла (AGENTS.md-стиль) | Хуки, quality gates, проверки в пайплайне |
| Можно проигнорировать? | Да, без технических последствий | Нет — блокирует или откатывает действие |
| Подходит для | Стиль кода, структура папок, нейминг | Токены, секреты, прод-доступ, ПДн, необратимые действия |

**Практическое следствие**: если в скилле написано "используй переменную
окружения для токена, не деплой без подтверждения" — это просьба, а не
гарантия. Для всего, что реально критично (токен Dokploy, доступ к проду,
необратимые операции), нужен отдельный enforcement-слой — линтер, CI-гейт,
скрипт-обёртка, которая физически не даст выполнить действие в обход правила.
Не полагайся на то, что агент "прочитал и не ошибся".

Чеклист при написании скилла: для каждого правила спроси — *"что будет,
если агент это правило проигнорирует?"* Если ответ "ничего страшного" —
оставляй как guidance. Если ответ "инцидент" — выноси в enforcement.

## Принцип 3. Скиллы — это цепочка (Golden Path), а не набор независимых инструкций

Синхронный Golden Path из документа:

```
Discovery → Design (SDD/DDD) → Prep → [ревью] → Deploy
```

Рекомендуемое разделение скиллов 1:1 с этим потоком:

| Этап | Задача скилла | Обязательный вход | Обязательный выход |
|---|---|---|---|
| **Discovery** | Зафиксировать гипотезу результата и критерии приёмки *до* любого кода | запрос пользователя | `intent.md` — намерение + критерии успеха |
| **Design** | Спроектировать структуру по SDD/DDD | `intent.md` | спецификация + структура папок/модулей |
| **Prep** | Собрать проект в исполняемый вид, тесты, конфиги | спецификация | готовый к сборке репозиторий + `feature-list.json` |
| **Deploy** | Задеплоить через Dokploy | репозиторий + Evidence Bundle | развёрнутый сервис + запись в аудит-лог |

Каждый скилл **не начинает работу**, если не получил обязательный
артефакт от предыдущего — это и есть машинопроверяемость: агент не может
"додумать" пропущенный шаг, потому что физически нет входного файла.

У Discovery-скилла отдельная важность: документ прямо называет
"Discovery Before Generation" одним из 11 принципов внедрения. Без него
агент додумывает намерение "как понял", и результат непредсказуем — даже
если Design и Prep сделаны идеально.

## Принцип 4. Обязательный набор структурных файлов в каждом проекте

Независимо от фреймворка и отдела, каждый проект, созданный через скиллы,
должен содержать:

| Файл | Назначение | Кто создаёт/обновляет |
|---|---|---|
| `AGENTS.md` | Контекст проекта для любого агента: архитектура, конвенции, что нельзя делать | Design |
| `NOTES.md` | Постоянная память проекта между сессиями агента | Все скиллы (дописывают) |
| `intent.md` | Гипотеза результата + критерии приёмки | Discovery |
| `feature-list.json` | Декомпозиция задачи на подзадачи | Design/Prep |
| `EVIDENCE.md` (или `evidence/`) | Что сделано, как проверено, ссылки на тесты/логи | Prep, читает Deploy |

Это единообразие — то, что делает проект "готовым к интеграции": любой
человек в компании (или другой агент) открывает `AGENTS.md` и сразу
понимает контекст, не читая весь код.

## Принцип 5. Аудит — append-only, всё синкается в git

- Ничего не переписывается "поверх" — только дописывается (append-only
  журнал). Если агент меняет решение — это новая запись в `NOTES.md`
  или `EVIDENCE.md`, а не стирание старой.
- Каждый скилл обязан **закоммитить** результат своей работы в git по
  завершении шага — даже промежуточный (WIP), а не оставлять состояние
  только в контексте диалога с агентом.
- Коммит-мессадж должен содержать ссылку на то, какой Evidence он
  подтверждает (что проверено и как).
- Deploy-скилл **не имеет права** запускаться, если `EVIDENCE.md` для
  соответствующего изменения отсутствует или неполный.

## Принцип 6. Уровень автономии зависит от обратимости действия

Документ вводит лестницу автономии R0–R5. Для целей скиллов достаточно
упрощённой версии:

| Этап | Обратимость | Рекомендуемый уровень | Что это значит |
|---|---|---|---|
| Discovery | Полностью обратимо | R4–R5 | Агент работает автономно |
| Design | Обратимо (черновик) | R3–R4 | Автономно, ревью по желанию |
| Prep | Обратимо (ветка/PR) | R2–R3 | Ревью перед merge |
| **Deploy** | **Труднообратимо / необратимо** | **R1–R2** | **Обязательное подтверждение человека перед вызовом Dokploy API** |

Правило по умолчанию: если действие трогает прод, деньги, доступ к внешним
сервисам или персональные данные — понижай автономию, даже если "агент
обычно справляется". Автономия — это результат зрелости процесса, а не
доверия к конкретной модели.

## Принцип 7. "Remix-first, write-second" — единый реестр скиллов

Перед тем как отдел пишет новый скилл — он обязан проверить, нет ли уже
готового в общем каталоге. Практическая реализация для тебя:

- один репозиторий/каталог скиллов на всю компанию, с метаданными
  (Принцип 1) в каждом файле;
- жизненный цикл скилла: `draft → review → published → in-use → deprecated`;
- владелец каталога (ты) решает, какие локальные наработки отделов
  сертифицировать и распространить на всех — это то самое "снизу-вверх с
  централизацией" из документа.

## Принцип 8. Скилл сам проверяет, не устарел ли он (авто-обновление)

Устаревание — один из четырёх типовых рисков Context Supply Chain из
документа: локальная копия скилла расходится с версией в реестре, и агент
работает по неактуальным правилам, а никто об этом не знает.

Решение — не полагаться на то, что кто-то вручную разошлёт новую версию,
а встроить проверку прямо в сам скилл.

**Механика:**

1. В метаданных скилла хранится `version` и `registry_url` (или путь к
   каталогу скиллов).
2. При **первом использовании скилла в сессии** (не на каждый вызов —
   это дорого по токенам и избыточно) агент выполняет дешёвую проверку:
   сравнивает локальную `version` с версией в реестре.
3. Результат проверки определяет, что делать дальше — см. таблицу:

| Разница версий | Действие |
|---|---|
| Совпадает | Работать дальше молча, ничего не сообщать пользователю |
| Патч/минорная (напр. 1.2.0 → 1.2.3) | Подтянуть автоматически, коротко уведомить пользователя одной строкой |
| Мажорная (напр. 1.x → 2.0) | **Не обновлять автоматически** — уведомить пользователя, что вышла версия с ломающими изменениями, и спросить подтверждение |
| Реестр недоступен | Работать на локальной версии, пометить в `EVIDENCE.md`, что проверка не выполнена (не блокировать работу из-за недоступности сети) |

**Почему именно "раз в сессию", а не при каждом вызове:**
частая проверка — это лишний сетевой вызов и токены на каждый шаг Golden
Path, а риск устаревания в рамках одной сессии пренебрежимо мал (сессия
обычно короче, чем цикл обновления скиллов). Раз в сессию — баланс между
актуальностью и стоимостью. Для критичных enforcement-скиллов (Deploy)
можно снизить интервал до "перед каждым необратимым действием" — это
дешевле, чем откат прод-инцидента из-за устаревшего правила.

**Важно:** проверка версии — это guidance-механизм (агент может её
пропустить, если сеть недоступна), а не enforcement. Не путай это с
обязательными правилами из Принципа 2 — auto-update не должен становиться
точкой отказа всего процесса.

## Чеклист перед публикацией скилла

- [ ] Есть YAML-метаданные (owner, version, status, scope, depends_on)
- [ ] Явно указано, какой артефакт скилл получает на входе и какой отдаёт на выходе
- [ ] Правила разделены на guidance и enforcement; для enforcement указан
      технический механизм (хук/линтер/CI), а не только текст
- [ ] Указан уровень автономии и обоснование (обратимость действия)
- [ ] Скилл требует существования обязательных структурных файлов проекта
      (или создаёт их сам)
- [ ] Описано, что и куда коммитится в git по завершении шага
- [ ] Указано, что происходит при ошибке / недостающем входном артефакте
      (скилл должен явно отказывать, а не "додумывать")
- [ ] Указан `registry_url` и правило проверки версии (частота, поведение
      при патче/минорной/мажорной разнице, поведение при недоступности реестра)
