# Code Design: архитектура проекта по DDD

## 1. Назначение (Purpose)

Раскладывает бэкенд по DDD и фиксирует контракты — так, чтобы разработчик
(человек или субагент) мог начинать писать код, не догадываясь, куда что
класть.

Три источника правды, и каждый отвечает за своё:

| Источник | Отвечает на вопрос | Кто ведёт |
|---|---|---|
| `MOCK.html` + критерии `intent.md` | **что** система делает | `/nlab:prototype` |
| `arch/` | **куда** что кладём и чего не видно из кода | этот скилл |
| `backend/domain/models.py` | **какие контракты** у данных | этот скилл, настоящим кодом |

Отдельного документа со схемами нет намеренно. Модели, написанные в
markdown, потом переписываются кодом — это одна и та же работа дважды и
источник расхождений. Контракт всё равно фиксируется **до** реализации, но
пишется один раз и сразу проверяется интерпретатором, а не глазами.

Единый язык из `arch/language.md` связывает всё: одно понятие называется
одинаково в разговоре с заказчиком, в макете и в именах классов.

Скилл опирается на документы реестра — **читай их с диска, не пересказывай
по памяти**: `${CLAUDE_PLUGIN_ROOT}/skills/project-start/assets/AGENTS.md` (§5 автономия,
§6 обязательные файлы) и
`${CLAUDE_PLUGIN_ROOT}/skills/project-start/references/project_setup_best_practices.md`
(§3 pydantic-ai, §6 модели).

Служебные артефакты процесса лежат в `project-docs/` (создана на этапе
`/nlab:project-start`); в корне из документов остаётся только `AGENTS.md`. Короткие
имена в тексте — файлы оттуда, в командах путь указан полностью.

Все пути ниже — относительно каталога этого скилла:

```
SKILL_DIR = ${CLAUDE_PLUGIN_ROOT}/skills/code-design
├── assets/arch/ARCH.md             # → project-docs/arch/ARCH.md
├── assets/arch/language.md         # → project-docs/arch/language.md
└── assets/arch/adr/0000-template.md  # → project-docs/arch/adr/, шаблон
```

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Скилл **не начинает работу** без выхода `/nlab:prototype` (а тот — без `/nlab:project-start`). Нет входа — не
додумывать, а отправить пользователя на предыдущий этап.

| Артефакт | Обязателен? | Кто предоставляет | Что делать, если отсутствует |
|---|---|---|---|
| `project-docs/intent.md` с непустыми критериями приёмки и границами | да | `/nlab:project-start` | остановиться, запустить `/nlab:project-start` |
| `project-docs/feature-list.json` с `mock_ref` у подзадач | да | `/nlab:prototype` | остановиться, запустить `/nlab:prototype` |
| `project-docs/MOCK.html`, согласованный | да, если у проекта есть интерфейс | `/nlab:prototype` | нет макета — требования не сняты; отправить на `/nlab:prototype`. Проект без интерфейса — отметить это в `NOTES.md` и продолжать |
| `project-docs/NOTES.md` с зафиксированным стеком | да | `/nlab:project-start` | стек не выбран — вернуться на Discovery, не выбирать молча за пользователя |
| Ответы на открытые вопросы из `intent.md` | да, если вопрос влияет на контракт | пользователь | спросить прямо; без ответа не проектировать «на всякий случай», а зафиксировать развилку в ADR и взять один вариант с пометкой «решение пересматривается» |
| Доменные знания: как заказчик называет вещи | да | пользователь | спросить его словами, а не терминами; единый язык нельзя выдумать за заказчика |

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| `backend/domain/models.py` | да | **настоящий код**: pydantic-модели входа/выхода, без логики. Импортируется — значит контракт валиден | Prep, реализация, субагенты |
| `arch/ARCH.md` §9 «Агент как сервис» | да, если проект — агент | артефакты, входы, модели и бюджет, права, improvement, проверки. Источник для генерации файлов Assay | `/agent-for-assay` при публикации |
| `project-docs/arch/agents.md` | да, если в проекте есть агент | mermaid-схема, что передаётся, где человек в контуре; иначе «не применимо» | Prep, реализация |
| `project-docs/arch/ARCH.md` | да | масштаб DDD, слои, порты, карта модулей, точки входа из макета, инструменты, границы автономии, данные, секреты, сквозные решения | Prep, любой новый участник |
| `project-docs/arch/language.md` | да | словарь понятий, запрещённые синонимы, слова-омонимы | все — это основа именования |
| `project-docs/arch/adr/NNNN-*.md` | да, на каждое значимое решение | ADR по шаблону: контекст, решение, альтернативы, последствия | ревью, будущие участники |
| Скелет папок бэкенда | да | `domain/`, `application/`, `infrastructure/`, `interfaces/` с `.gitkeep` | Prep |
| `project-docs/feature-list.json`, дополненный | да | у каждой подзадачи — `module` (куда ляжет код); `mock_ref` от `/nlab:prototype` сохраняется | Prep, декомпозиция на субагентов |
| `project-docs/PLAN.html`, пересобранный | да | тот же файл, что создал `/nlab:project-start`, — плюс раздел «Как устроено внутри» и обновлённые статусы задач. **Генерируется**, руками не правится | пользователь, приёмка, заказчик |
| `.env.example`, пересобранный | да, если решения Design поменяли зависимости | ключи под фактически выбранные хранилище/сервисы, значения `CHANGE_ME_*` | Prep, Deploy |
| Записи в `project-docs/NOTES.md` и `EVIDENCE.md` | да | append-only | аудит, Deploy |

Всё коммитится по завершении. Коммит-мессадж указывает, на основании
какого входа сделано проектирование (`MOCK.html` + `intent.md` → `arch/` + модели).

## 4. Guidance — рекомендации (можно проигнорировать без тех. последствий)

### Язык домена — первым, до всего остального

Единый язык заполняется **до** раскладки модулей, потому что имена в нём
становятся именами классов, таблиц и папок. Берётся из того, как говорит
заказчик, а не из того, как удобно программисту. Если заказчик называет
одно и то же двумя словами — выбрать одно, второе записать в запрещённые.
Если одно слово в двух местах значит разное — это найденная граница между
доменными областями, а не повод придумать префикс.

### DDD по размеру задачи

| Уровень | Когда применять |
|---|---|
| Слои `domain` / `application` / `infrastructure` + единый язык | **всегда**, это минимум |
| + агрегаты и репозитории | есть инварианты, которые нельзя нарушить частичной записью |
| + границы доменных областей | доменных областей больше одной; одно слово значит разное |

Полный DDD на маленьком сервисе — три слоя абстракции ради одной таблицы.
Выбранный уровень и причина — в `arch/ARCH.md` §1 и в ADR. Повышать
уровень позже дешевле, чем разбирать преждевременную конструкцию.

### Правило зависимостей

Только внутрь: `interfaces → application → domain`, `infrastructure →
domain`. Домен не знает про HTTP, БД, файлы, очереди и LLM. Внешний мир
подключается через порты: домен объявляет интерфейс, инфраструктура
реализует. Это и есть то, что делает домен тестируемым без поднятой базы и
без ключа LLM, — а не «красивая архитектура» сама по себе.

### Контракт — это код, а не документ о коде

Модели вход/выход пишутся сразу в `backend/domain/models.py` настоящими
pydantic-классами: только типы и docstring, без логики. Это тот же самый
«контракт до реализации», но написанный один раз и проверяемый
интерпретатором, а не глазами.

Что при этом **не** пишется: markdown-файл, повторяющий те же модели
словами. Если модель нуждается в пояснении, которого не выразить типом, —
docstring в самом классе, а не отдельный документ.

Инструменты агента — типизированные, через pydantic-ai; API писать по
<https://ai.pydantic.dev/llms.txt>, а не по памяти. Сигнатуры инструментов
живут в коде; в `arch/ARCH.md` §4b фиксируется только то, чего код не
говорит: что инструмент трогает снаружи и обратимо ли действие.

### Если проект — агент, решай «как сервис» сразу

Агент, которого будут вызывать извне, рано или поздно поедет на платформу
(у нас это Assay). Файлы публикации туда пишет отдельный скилл
`/agent-for-assay` в момент подачи — **их формат мы у себя не копируем**:
платформа в пилоте, схемы меняются, а вторая копия формата протухает молча.

Но решения, из которых эти файлы собираются, дороги задним числом, поэтому
фиксируются здесь, в `arch/ARCH.md` §9:

- **что агент отдаёт наружу файлами** — не только модель в ответе, а
  именованные артефакты: по ним потом считается качество прогона;
- **что он принимает** — всё нужное объявлено входом; контекст-подсказка
  («кто вызвал», «зачем») не гарантирован;
- **класс модели и fallback по стадиям** — на 503 и «перегружено» падаем на
  следующую модель, а не умираем. Это спасает и без всякой платформы;
- **бюджет токенов** и остановка до его исчерпания, а не после;
- **владелец, видимость, права** по наименьшей привилегии;
- **согласие на автономное улучшение** — «да» требует репозитория в
  организации `sber-nlab`;
- **критерии приёмки в машинопроверяемом виде** — это же основа тестов.

Проект не агент — написать «не применимо» и идти дальше. Раздел не удалять:
иначе непонятно, решение это или забыли.

### Решения фиксируются как ADR

Значимое решение — то, которое дорого отменить: выбор хранилища, границы
областей, синхронный или фоновый режим, где человек в контуре, форма
ключевых моделей данных. Каждое —
отдельным ADR с альтернативами и последствиями. Отдельно обязателен ADR на
**любое отклонение** от дефолтов компании (стек, фронтенд-темплейт,
pydantic-ai, доступ к LLM только через API, выданный репозиторий) — с
явным согласием пользователя.

### Декомпозиция под субагентов

Проектные решения субагентам не делегируются — их принимает основная
сессия (Fable-5/Opus-5) и фиксирует в `arch/`. Субагентам на
Sonnet-5 уходит реализация: одна подзадача `feature-list.json` — один
субагент, и в задаче даётся **элемент макета и модуль**, а не пересказ.
Поэтому у каждой подзадачи должны быть `mock_ref` и `module`.

### План — представление, а не третий источник правды

`project-docs/PLAN.html` создаёт `/nlab:project-start` сразу после
Discovery. Этот этап его **пересобирает**: добавляет раздел «Как устроено
внутри» — из каких частей состоит система и кто за что отвечает, без кода —
и обновляет статусы задач. Отдельный документ не заводится: два описания
одного проекта неизбежно разойдутся.

Жёсткое правило: **план генерируется из `feature-list.json` и никогда не
правится руками.** Меняются задачи — план пересобирается целиком. Иначе
через месяц план и реальные задачи разойдутся, и никто не поймёт, какой из
них настоящий. Шаблон — `${CLAUDE_PLUGIN_ROOT}/skills/project-start/assets/plan.template.html`; в подвале
проставляется, из какого коммита `feature-list.json` собран.

### Этап закрывает свои же подзадачи

Design выполняет часть подзадач сам (спецификация, схема агентов, карта
модулей). Отметить их `status: done` в `feature-list.json` — часть работы
этапа, а не чужая забота. Иначе на приёмке видно «сделано 0 из N», хотя
половина закрыта.

### Как разговаривать с пользователем

Правила из `/nlab:project-start` §4 действуют и здесь — включая уровень подачи,
записанный в проектном `AGENTS.md`. Они про всю сессию, а не
про один скилл. На этом этапе особенно важно: архитектура звучит для
не-инженера как заклинание. Объясняй решения через последствия для него
(«домен не знает про базу — значит, сможем поменять хранилище, не переписав
логику»), а не через названия паттернов. Термин при первом употреблении —
одна поясняющая фраза. Не спрашивай, какой слой куда положить: это твоя
работа. Спрашивай то, чего не знаешь ты, — как называются вещи в его
предметной области.

## 5. Enforcement — обязательные правила (нарушение = блокировка)

| Правило | Технический механизм принуждения | Когда |
|---|---|---|
| Макет разобран целиком | Проверка **R**: каждый `data-mock-id` из `MOCK.html` есть в таблице точек входа `arch/ARCH.md` §4a либо явно отмечен в §8 как осознанно не реализуемый | перед handoff |
| Проектирование не начинается без согласованного макета | Отсутствует `intent.md`, `MOCK.html` или `feature-list.json` с `mock_ref` → скилл останавливается и отправляет на `/nlab:prototype` | на старте |
| Архитектура допроектирована | Проверка **H**: в `arch/` не осталось `TODO`. Есть — handoff не отдаётся | перед handoff |
| Каждый критерий приёмки покрыт | Проверка **I**: критериев в `intent.md` не меньше нуля и подзадач хотя бы столько же; у каждой подзадачи есть `module`, и такой модуль есть в карте `arch/ARCH.md` | перед handoff |
| Модели — настоящий валидный код | Проверка **J**: `backend/domain/models.py` существует, компилируется и содержит хотя бы одну модель. Проверяет интерпретатор, а не человек | перед handoff |
| Домен не зависит от инфраструктуры | Проверка **K**: в `domain/` нет импортов фреймворков, драйверов БД, HTTP-клиентов и SDK. Есть — правило зависимостей нарушено, слои спроектированы неверно | перед handoff и далее при каждом коммите кода |
| Схема агентов связна | Проверка **L**: в `arch/agents.md` каждый узел, участвующий в стрелке, объявлен; либо явное «не применимо» | перед handoff |
| Решения по агенту приняты, а не забыты | Проверка **S**: если проект — агент, в `arch/ARCH.md` §9 заполнены все шесть подразделов; если не агент — стоит явное «не применимо». Пустой раздел означает, что решение не принято | перед handoff |
| Каждый ADR виден в архитектуре | Проверка **M**: любой файл `arch/adr/NNNN-*.md`, кроме шаблона, упомянут в `arch/ARCH.md`. Иначе решение принято и потеряно | перед handoff |
| Отклонение от дефолта компании — только с ADR и согласием | Отклонение без ADR, содержащего явное согласие пользователя, не допускается; при сомнении — считать enforcement и остановиться | всегда |

Команды проверок — выполнять как есть, результат каждой записывать в
`EVIDENCE.md` (п.8). Все запускаются из корня проекта.

```bash
# H. Архитектура допроектирована. Ожидание: OK.
# Точный маркер, не любое слово TODO. Исключены строки-цитаты (пояснения в
# шапках шаблонов сами его упоминают) и append-only «Журнал изменений».
python3 - <<'PY'
import pathlib, re
MARK = "TODO (этап Design)"
hits = []
for f in sorted(pathlib.Path("project-docs/arch").rglob("*.md")):
    body = re.split(r"^##\s*Журнал изменений", f.read_text(), maxsplit=1, flags=re.M)[0]
    for i, line in enumerate(body.splitlines(), 1):
        if MARK in line and not line.lstrip().startswith(">"):
            hits.append(f"{f}:{i}: {line.strip()}")
print("\n".join(hits) if hits else "OK: незакрытых разделов нет")
PY

# I. Подзадачи разложены по модулям. Ожидание: OK.
python3 - <<'PY'
import json, re, pathlib
data = json.loads(pathlib.Path("project-docs/feature-list.json").read_text())
if not isinstance(data, list):
    print("feature-list.json должен быть массивом верхнего уровня"); raise SystemExit(1)
arch = pathlib.Path("project-docs/arch/ARCH.md").read_text()
known = set(re.findall(r"`([a-z][\w./-]*)`", arch))
errs = [f"{f.get('id')}: нет поля module" for f in data if not f.get("module")]
errs += [f"{f.get('id')}: модуль '{f['module']}' не упомянут в arch/ARCH.md"
         for f in data if f.get("module") and f["module"] not in known]
t = pathlib.Path("project-docs/intent.md").read_text()
b = re.search(r"##\s*Критерии приёмки\s*\n(.*?)(?=\n##\s|\Z)", t, re.S)
crit = re.findall(r"^\s*\d+\.", b.group(1), re.M) if b else []
if crit and len(data) < len(crit):
    errs.append(f"критериев {len(crit)}, подзадач {len(data)} — часть не покрыта")
print("\n".join(errs) if errs else f"OK: {len(data)} подзадач разложены по модулям")
PY

# J. Модели — валидный код. Ожидание: OK.
# Проверяет интерпретатор, а не человек: файл либо импортируется, либо нет.
python3 - <<'PY'
import pathlib, re, sys, types
f = pathlib.Path("backend/domain/models.py")
```

## 8. Логирование и аудит

В `EVIDENCE.md` — проверяемые записи, а не оценки:

- входы приняты: `intent.md`, `MOCK.html`, `feature-list.json` — есть;
  критериев приёмки — N, элементов макета — N;
- единый язык: понятий — N, запрещённых синонимов — N, слов-омонимов — N;
- выбранный масштаб DDD и ADR, в котором это обосновано;
- проверка **H** — команда и результат (`TODO` не осталось);
- проверка **I** — покрыто критериев N из N; ссылки на подзадачи валидны;
- проверка **J** — модели компилируются; импорт выполнен или отложен до
  Prep (указать, какого модуля не хватило);
- проверка **K** — запрещённых импортов в `domain/` — 0;
- проверка **L** — схема связна либо «не применимо» с обоснованием;
- проверка **M** — ADR без упоминания в `ARCH.md` — 0; всего ADR — N;
- подзадач с `module` — N из N; закрыто самим этапом Design — N;
- проверка **R** — элементов макета без точки входа — 0;
- проверка **S** — §9 заполнен (артефактов N, стадий N, improvement решён) либо «не применимо»;
- `PLAN.html` пересобран, раздел «Как устроено внутри» заполнен (коммит в подвале);
- `.env.example` пересобран / не потребовал изменений (указать почему).

В `NOTES.md` — решения и обоснования: масштаб DDD, границы областей,
хранилище, где человек в контуре, каждое отклонение от дефолта компании с
пометкой «решение пользователя» и ссылкой на ADR.

`update_check: per_session` — один раз при первом использовании скилла в

| Разница версий | Действие |
|---|---|

работу.
