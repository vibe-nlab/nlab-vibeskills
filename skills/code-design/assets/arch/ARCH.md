## 1. Масштаб решения

DDD применяется по размеру задачи, а не «всегда по максимуму». Отметить,
что выбрано, и почему — это решение уходит в ADR.

| Уровень | Когда | Выбрано? |
|---|---|---|
| **Слои** — `domain` / `application` / `infrastructure`, единый язык | всегда, минимум | да |
| **+ Агрегаты и репозитории** | есть инварианты, которые нельзя нарушить частичной записью | |
| **+ Границы контекстов** (отдельные модули с собственным языком) | доменных областей больше одной, одно слово значит разное | |

Обоснование выбора: <почему именно этот уровень; ссылка на ADR>.

## 2. Слои

Обязательный минимум для любого бэкенда. Правило зависимостей — только
внутрь: `infrastructure → application → domain`. Домен не знает ничего о
HTTP, БД, файлах, брокерах и LLM.

| Слой | Что внутри | Что ему **запрещено** |
|---|---|---|
| `domain/` | понятия из `arch/language.md`, правила предметной области, инварианты | импорты фреймворков, БД, HTTP-клиентов, SDK |
| `application/` | сценарии: оркестрация домена, транзакции, вызовы портов | прямые SQL-запросы, разметка ответов HTTP |
| `infrastructure/` | адаптеры: БД, HTTP, LLM-провайдер, файлы, очереди | бизнес-правила |
| `interfaces/` | точки входа: API-роуты, CLI, обработчики агента | бизнес-правила |

Внешний мир подключается через **порты**: домен объявляет интерфейс, а
инфраструктура его реализует. Это то, что делает домен тестируемым без
поднятой базы и без ключа LLM.

| Порт (объявлен в) | Реализация (в) | Зачем |
|---|---|---|

## 4. Границы доменных областей

Заполняется, только если в п.1 выбран уровень с границами контекстов.
Иначе — «одна доменная область, границы не выделяются».

| Область | За что отвечает | Что отдаёт наружу | Что принимает |
|---|---|---|---|

Как области общаются между собой: через типизированные модели, не через
общую базу. Общая таблица на две области — это признак, что граница
проведена неправильно.

## 4a. Точки входа

Из макета: какой элемент интерфейса какую операцию запускает. Модели
вход/выход **не дублируются** — они объявлены в `backend/domain/models.py`,
здесь только имя.

| Элемент макета (`data-mock-id`) | Операция | Модель входа | Модель выхода |
|---|---|---|---|
| | | `SomethingIn` | `SomethingOut` |

## 4b. Инструменты агента

код не говорит: что инструмент трогает снаружи и можно ли откатить.

| Инструмент | Что делает | Внешние системы | Обратимость | Что при отказе |
|---|---|---|---|---|
| | | | обратимо / необратимо | |

## 4c. Границы автономии

## 9. Агент как сервис

Заполняется, **только если проект — агент, который будут вызывать извне**
(в том числе через платформу Assay). Обычный сервис или библиотека —
пометить раздел неприменимым: отдельной строкой сразу под этим заголовком
написать `Не применимо` и причину. Раздел при этом не удалять, иначе
непонятно, решение это или забыли.

Здесь фиксируются решения, которые дорого принимать задним числом. Файлы
публикации (`agent-card.json`, `assay.agent.yaml`, `contracts/*.yaml`,
`PIPELINE.md`) **генерируются отсюда** скиллом `/agent-for-assay` в момент
подачи — копию формата платформы у себя не держим, она меняется.

### 9.1 Выходные артефакты

Что агент отдаёт наружу **файлами**, а не только моделями в ответе. Именно
по ним потом считается качество прогона.

| Артефакт | Тип | Обязателен | Что внутри |
|---|---|---|---|
| `report.json` | file | да | |

### 9.2 Входы прогона

Всё, что нужно пайплайну, объявляется входом. Контекст, который приходит
«подсказкой» (кто вызвал, зачем), не гарантирован — нужен, значит объявляй.

| Вход | Тип | Обязателен | Что делать, если не пришёл |
|---|---|---|---|

### 9.3 Стадии, модели и бюджет

Класс модели, а не конкретный id: «сильная» / «дешёвая» по стадии.
**Fallback обязателен** — на 503 и «перегружено» падаем на следующую
модель, а не умираем.

| Стадия | Класс модели | Fallback | Бюджет токенов |
|---|---|---|---|

Поведение при исчерпании бюджета: остановиться **до** исчерпания и честно
отчитаться, а не выяснять постфактум.

### 9.4 Владелец, видимость и права

Наименьшие привилегии: только те пути и инструменты, которые пайплайн
реально использует.

| Поле | Значение |
|---|---|
| Команда-владелец | |
| Видимость | private / org |
| Читает | |
| Пишет | |
| Инструменты | из §4b |

### 9.5 Согласие на автономное улучшение

`improvement`: **да / нет**, и почему.

«Да» означает, что платформа сможет сама открывать pull request с
улучшениями, и **требует, чтобы репозиторий жил в организации
`sber-nlab`** — иначе это не сработает. «Нет» — получаем только
рекомендации.

### 9.6 Проверки качества

Критерии приёмки из `intent.md` в машинопроверяемом виде: над каким
артефактом, что именно проверяется, насколько критично. Это же основа для
тестов — полезно независимо от публикации.

| Критерий из `intent.md` | Что проверяем | Артефакт | Критичность |
|---|---|---|---|
| | | | high / medium / low |
