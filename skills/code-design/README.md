# /nlab:code-design — архитектура проекта по DDD

Третий этап Golden Path. Берёт согласованный макет от `/nlab:prototype` и
раскладывает по нему бэкенд. После него можно писать код, не догадываясь ни о
контрактах, ни о том, куда что класть.

Три источника правды, каждый отвечает за своё:

| Источник | Вопрос | Кто ведёт |
|---|---|---|
| `MOCK.html` + критерии `intent.md` | **что** система делает | `/nlab:prototype` |
| `project-docs/arch/` | **куда** что кладём и чего не видно из кода | этот скилл |
| `backend/domain/models.py` | **какие контракты** у данных | этот скилл, настоящим кодом |

Отдельного документа со схемами нет намеренно: модели, написанные в
markdown, потом переписываются кодом — это одна работа дважды и источник
расхождений. Контракт всё равно фиксируется до реализации, но пишется один
раз и проверяется интерпретатором.

Единый язык из `arch/language.md` связывает всё: одно понятие называется
одинаково в разговоре с заказчиком, в макете и в именах классов.

## DDD по размеру задачи

Скилл не навязывает полный DDD маленькому сервису:

| Уровень | Когда |
|---|---|
| слои `domain` / `application` / `infrastructure` + единый язык | всегда, это минимум |
| + агрегаты и репозитории | есть инварианты, которые нельзя нарушить частичной записью |
| + границы доменных областей | доменных областей больше одной, одно слово значит разное |

Выбранный уровень и причина фиксируются в `arch/ARCH.md` и в ADR. Поднять
уровень позже дешевле, чем разбирать преждевременную конструкцию.

## Установка

Скилл входит в плагин `nlab` — ставится вместе со всем пакетом. См.
[README реестра](../../README.md).

## Использование

1. Откройте Claude Code в проекте, который уже прошёл `/nlab:prototype`.
2. Наберите `/nlab:code-design`.
3. Отвечайте на вопросы про предметную область — своими словами: как
   называются вещи, чем одно отличается от другого. Именно из этого
   собирается единый язык, а из него — имена в коде.
4. На выходе — заполненный `arch/`, `backend/domain/models.py` с моделями,
   скелет папок бэкенда, подзадачи с привязкой к модулям и пересобранный
   `PLAN.html`: в нём появляется раздел «Как устроено внутри».

## Что проверяется автоматически

Правила без механической проверки остаются просьбами, поэтому:

| | Что ловит |
|---|---|
| **H** | в `arch/` остались `TODO` — handoff не отдаётся |
| **I** | критерий приёмки не покрыт подзадачей, или ссылка ведёт в никуда |
| **J** | `backend/domain/models.py` не импортируется или там нет ни одной модели |
| **K** | домен импортирует БД, HTTP или SDK — слои спроектированы неверно |
| **L** | в схеме агентов стрелка ведёт к необъявленному узлу |
| **M** | ADR написан, но нигде не упомянут — решение принято и потеряно |
| **R** | элемент макета без точки входа в `ARCH.md` — пропущенная работа |
| **S** | проект-агент, а решения «как сервиса» не приняты — или раздел не помечен неприменимым |

## Если проект — агент

В `arch/ARCH.md` появляется раздел **§9 «Агент как сервис»**: что агент
отдаёт наружу файлами, что принимает на вход, какой класс модели и fallback
у каждой стадии, бюджет токенов, владелец и права, согласие на автономное
улучшение, критерии приёмки в машинопроверяемом виде.

Это решения, которые дорого принимать задним числом, и они полезны сами по
себе — fallback спасает от падения на перегруженной модели, бюджет от
тихого сжигания денег.

Файлы публикации на платформу (`agent-card.json`, `assay.agent.yaml`,
`PIPELINE.md`) отсюда **генерируются** скиллом `/agent-for-assay` в момент
подачи. Их формат мы у себя не копируем: платформа в пилоте, схемы
меняются, а вторая копия формата протухает молча.

Проект не агент — раздел помечается строкой `Не применимо` с причиной.
