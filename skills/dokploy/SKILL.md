# Dokploy: деплой и эксплуатация

## 1. Назначение (Purpose)

Завершающий скилл Golden Path (`Discovery → Design → Prep → Deploy`):
берёт подготовленный скиллом `dokploy-prep` репозиторий и разворачивает его
на Dokploy-сервере через Dokploy API, а дальше сопровождает сервис
(redeploy, логи, env, домены, диагностика). Ты — деплой-агент: всё делаешь
сам через API, у пользователя спрашиваешь только то, что реально за ним:
доступы к серверу (при первом подключении), выбор сервера/домена, решения
по прод-данным.

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Не начинай деплой, если обязательный вход отсутствует, — не «додумывай»
пропущенный шаг, а явно скажи, чего не хватает, и остановись.

| Артефакт | Обязателен? | Кто предоставляет | Если отсутствует |
|---|---|---|---|
| Репозиторий на GitHub, код запушен (`git status`, `git rev-parse HEAD origin/<branch>`) | да | пользователь | остановиться, попросить запушить — Dokploy тянет из GitHub, локальные правки не попадут |
| Для проектов компании: репозиторий — выданный централизованно (см. project_setup_best_practices.md п.5: создаёт ответственный по запросу в Telegram) | да — для Golden-Path-проектов | ответственные @sanchezgl / @KirillBorovkov | остановиться, попросить пользователя запросить репо и передать свой GitHub-никнейм; свой репозиторий не создавать |
| `docker-compose.dokploy.yml` + `.env.dokploy.example` + `DEPLOY_DOKPLOY.md` | да (для нового деплоя) | скилл `dokploy-prep` | запустить `/nlab:dokploy-prep`, если установлен; иначе подготовить самому по его конвенциям, закоммитить — и только потом продолжать |
| `servers.md` (реестр серверов, см. п.6 Шаг 0) | да | этот скилл (онбординг) | провести онбординг сервера — Шаг 0 |
| `EVIDENCE.md` проекта | да — для проектов, ведущихся по Golden Path | скилл Prep | остановиться и предупредить: деплой без evidence — отклонение от процесса, нужен явный ОК пользователя; ОК зафиксировать в `EVIDENCE.md` |

Для эксплуатации уже задеплоенного сервиса (redeploy, логи, диагностика,
env, домены) обязателен только `servers.md`.

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| Развёрнутый/обновлённый сервис | да | URL'ы, прошедшие health-проверку | пользователь |
| `<creds-dir из servers.md>/<проект>-creds.md` | да (новый деплой) | сервер, URL'ы, логины/пароли/ключи, projectId/composeId, репо/ветка/compose path | будущая эксплуатация |
| Запись в `EVIDENCE.md` проекта | да | append-only, см. п.8 | аудит, следующие сессии |
| Запись в `NOTES.md` проекта | да | что сделано, какие решения приняты и почему | любой следующий агент |
| Отчёт пользователю | да | таблица: сервер, домены, статусы, где креды, что осталось за пользователем | пользователь |

Правки репозитория (compose, доки) — закоммичены и запушены **до** деплоя.
Креды и `servers.md` в git не попадают никогда (см. п.5).

## 4. Guidance — рекомендации

- **Конвенции compose-файла** (`docker-compose.dokploy.yml`): без
  Traefik-лейблов и без проброса портов на хост (TLS и роутинг делает
  Traefik Dokploy через доменные записи); веб-сервисы — во внешней сети
  `dokploy-network` (`external: true`) **и** во внутренней сети для БД;
  БД — только во внутренней сети; данные — в named volumes; секреты и
  домены — через `${...}` из Environment сервиса. Полные правила — в скилле
  `dokploy-prep`.
- Поддомены бери от wildcard-домена сервера (из `servers.md`), если
  пользователь не дал свои.
- Секреты генерируй свежие (`python3 -c "import os,base64,secrets,string; ..."`) —
  не копируй с dev.
- Статус деплоя отслеживай поллингом `compose.one` → `composeStatus`
  (`running` → `done`/`error`), интервал 15 секунд.
- Пиши по-русски; после любой операции — короткий итог таблицей.
- **Проект Dokploy = кластер сервисов, а не один сервис.** На главном
  сервере лаборатории (`nlab-prod-sbercloud`, `dokploy.a.nlabstudio.ru`)
  проекты уже заведены: `infra` (хранилища, RAG-цепочка, wiki, память,
  MCP-гейт), `Nlab`, `agents`, `tools`, `research` (что куда — п.4a). Новый сервис — это compose или
  application **внутри** подходящего проекта; `project.create` только для
  нового кластера. Имя сервиса = имя репозитория без префиксов, `appName`
  задавай явно вида `<проект>-<репо>` (Dokploy допишет суффикс). Карта, кто
  куда относится, — `Infrastructure/docs/dokploy-projects.md`.
- **Без SSH тоже можно эксплуатировать**: лог сборки/деплоя —
  `deployment.readLogs`, состояние контейнеров (running / restarting /
  exited) — `docker.getContainers`, список маршрутов панели —
  `settings.getOpenApiDocument` (см. references/api.md). Чего API не отдаёт —
  stdout контейнера; падающий в рестарт-цикле контейнер воспроизводи
  локально: образ собирается тем же Dockerfile, ошибка та же.
- **Старый сервис на новом сервере = свежая сборка.** Незакреплённые
  зависимости в Dockerfile подтянут новые мажорные версии (проверено:
  `mcp>=1.2.0` без верхней границы получил 2.x и уронил контейнер). Перед
  переносом проверь пины в Dockerfile/requirements, а не только compose.
- **Проверь исходящий доступ сервера.** Провайдеры блокируют по IP:
  с `nlab-prod-sbercloud` (SberCloud) OpenRouter отвечает 403 «Access denied
  by security policy», хотя тот же ключ с других серверов работает. Если
  сервис после деплоя падает на внешнем API — сначала `curl` с сервера
  (или из ошибки самого сервиса), потом уже код. Ограничения фиксируй в
  реестре (`egress:`), решение о VPN/прокси — за владельцем сервера.
- **LLM с таких серверов — только через гейт лаборатории** (`llm-gateway` в
  реестре; на `nlab-prod-sbercloud` это `https://ai.nlabstudio.ru`, закрыты
  OpenRouter, OpenAI и Anthropic разом). OpenAI-совместимым клиентам —
  `LLM_BASE_URL=https://ai.nlabstudio.ru/v1`, Anthropic SDK —
  `ANTHROPIC_BASE_URL=https://ai.nlabstudio.ru` (так живёт `nlab-llm-wiki`);
  ключ гейта выдают ответственные, как и ключ OpenRouter. Сервис, перенесённый
  с другого сервера с прямым `openrouter.ai` / `api.openai.com` в env, здесь
  не заработает — сверь env с `egress:` до деплоя, а не по логам после.
- **Перенос данных между серверами без SSH** — только снапшотом через
  one-shot сидер в compose: снапшот кладётся в MinIO (анонимный префикс или
  header-auth; presigned query-string через nginx MinIO ломается), сервис
  `*-loader` с `restart: "no"` восстанавливает его при пустом томе, приложение
  ждёт `service_completed_successfully`. Пример — `qdrant-loader` в
  `sber-nlab/rag-v2/docker-compose.dokploy.yml`. Скопировать том напрямую
  без SSH нельзя, а «временный контейнер» вне Dokploy запрещён (п.5).
- **Сетевые вызовы — с ретраем.** API Dokploy и health-проверки повторяй
  до пары минут (пауза 5 с), прежде чем объявлять сервер недоступным:
  VPN/сеть оператора флапает чаще, чем падает сервер.
- **API-ключ, созданный через API, живёт 10 запросов в сутки.** `user.createApiKey`
  ставит `rate_limit_enabled=true`, `rate_limit_max=10`, окно 24 ч. Исчерпав
  лимит, ключ отдаёт `401` на всё подряд — выглядит как отозванный; в логах
  панели `Error verifying API key Error: Rate limit exceeded`. Ключи из UI
  лимита не имеют. Для скилла создавай с `rateLimitEnabled: false` и проверяй,
  что флаг применился. **Признак именно этой ошибки:** под тем же пользователем
  UI работает, а ключ получает 401 даже на `project.all`.
- **Роль `admin` отменяет галочки `can*`.** Они действуют только для `member`:
  у админа в базе `canAccessToSSHKeys=false`, а `sshKey.all` отдаёт 200. Кого
  нужно реально ограничить — оставляй `member`.
- **В `user.assignPermissions` поле `id` — это `userId`, а не `member.id`.**
  С неверным идентификатором API отвечает `200` и молча ничего не меняет;
  проверяй результат чтением, а не кодом ответа. В схеме БД к тому же опечатка:
  API принимает `accessedProjects`, колонка называется `accesedProjects` (одна `s`),
  то же у `accesedServices` — запрос к базе по «правильному» имени падает, и
  кажется, что права не сохранились.
- **Секреты — Vault-провайдером, а не значениями в Environment.** Интеграция
  встроена и лицензии не требует: `vaultProvider.create` (`hashicorp`, `infisical`,
  `aws`, `doppler`, `azure`, `scaleway`, `phase`), `testConnection`,
  `listSecretNames`. В Environment пишется ссылка
  `${{vault.<провайдер>.<путь>:<поле>}}`, значение подставляется при деплое.
  Провайдер привязывается к проектам через `assignments: [{projectId, environmentIds}]` —
  без этого любая ссылка отдаёт `403 not enabled for the given project`.
  В `vaultProvider.update` обязательно передавать `token` внутри `config`,
  иначе валидация падает с `config: expected string, received undefined`.
  Если Vault запечатан (после перезапуска его контейнера — не только машины),
  `testConnection` отдаёт `503 token validation failed`, а деплои со ссылками падают.
- **Тело запроса к API — UTF-8 и `Content-Type: application/json` без `charset`.**
  С `charset=utf-8` парсер панели тело не разбирает (`composeId: expected string,
  received undefined` на корректный payload). Кириллица, отправленная из shell в
  не-UTF-8 кодировке (консоль Windows, `LANG=C`), сохраняется как `����` — так
  выглядело описание сервиса. JSON с кириллицей пиши в файл в UTF-8 и отправляй
  `curl --data-binary @body.json`, не строкой в командной строке.
- **Бэкапы в MinIO: в destination обязателен `Provider = Minio`.** Dokploy делает
  их через rclone, и с `provider=AWS` тот игнорирует `--s3-force-path-style`,
  обращаясь к `<бакет>.<домен>` — такого DNS-имени нет. Симптом:
  `dial tcp: lookup <бакет>.<домен>: no such host`.

## 4a. Куда класть сервис — решения до деплоя

**Проект-кластер.** Критерии и примеры записаны в поле `description` каждого
проекта в панели — `project.all` их отдаёт. Читай их перед выбором, там уже
перечислено, какие сервисы куда; на `nlab-prod-sbercloud` сейчас так:

| проект | что туда (из описания в панели) |
|---|---|
| `infra` | инфраструктура лаборатории: S3-шлюз, RAG-цепочка (mdsvc → rag-prep → rag-v2), слои знаний и памяти (llm-wiki, memory-service), MCP-гейт |
| `Nlab` | приложения с агентом внутри — продукты лаборатории (dsp) |
| `agents` | агенты и хаб агентов (open-webui, emotional-glue, sml, zayavki, intelect-teacher, metodology); терминальный агент без UI — сюда |
| `tools` | рабочие инструменты сотрудников (транскрибатор, crm-gantt, xtab, bitrix-mcp) |
| `research` | демо, стенды и исследовательские платформы (lena, kurpatov-*, smysly-relay, viewer) |

Сомневаешься — спроси владельца, а не угадывай: переезд сервиса между
проектами меняет `appName` и ломает сетевые алиасы соседей.

**В Dokploy или нативным compose на сервере.** По умолчанию — в Dokploy, всегда.
Исключение одно: сервис, от которого зависит сам Dokploy, либо который обязан
пережить переустановку панели. Такой ставится в `/opt/<сервис>/` обычным
`docker compose` и подключается к сети `dokploy-network` — Traefik подхватит его
по лейблам, домен и TLS будут как у обычного сервиса.

Практически под это исключение попадает **Vault**: Dokploy читает из него секреты
при деплое, и держать его внутри Dokploy — цикл. Помни, что установщик Dokploy
начинает с `docker swarm leave --force` и сносит всё, что развёрнуто панелью.

Это не отменяет п.5: разовые `docker run` для «посмотреть» по-прежнему запрещены,
речь о постоянных стеках с compose-файлом в git.

**База данных.** По умолчанию — своя в стеке проекта, только в сети `internal`
(см. `dokploy-prep`). Общая БД на несколько стеков — только для платформенных
сервисов и только через сетевой алиас; имя контейнера у Dokploy случайное.

Отдельный вопрос — бэкапы: у сервиса в панели есть вкладка **Backups**, но она
ничего не делает, пока в организации не заведён **destination** (S3-хранилище).
Заводится один раз на сервер, дальше выбирается из списка. Для БД с данными,
которые нельзя потерять, расписание бэкапа — часть деплоя, а не «потом».

**Vault — кто что кладёт.** `platform/<сервис>` пишет владелец сервера,
`<проект>/<секрет>` — команда проекта своим токеном; токена нет — значения
кладёт владелец по запросу, в чат они не идут. Сам Dokploy читает всё через
провайдер (`vault-provider` в реестре), но **только в проектах из его
`assignments`**: перед первым деплоем с `${{vault…}}` проверь
`vaultProvider.all` → нужный `projectId` в списке; нет — это делает владелец
(`vaultProvider.update`), у тебя прав нет. Vault нужен в момент деплоя, не в
рантайме: запечатанный Vault или истёкший токен провайдера ломают деплой
(`503 token validation failed`), а работающие сервисы не трогают.

**S3 — три разных пути, не путать.**

| что кладём | как | нужны ли ключи S3 приложению |
|---|---|---|
| трейсы и артефакты MLflow | через сам MLflow (`--serve-artifacts`) | нет |
| файлы, которые агент отдаёт пользователю | presigned-ссылка от `s3-gateway` по его API-ключу | нет, только ключ гейта |
| данные инфраструктурного сервиса | прямой S3-ключ со скоупом на свой бакет, из Vault | да |

Прямой ключ — крайний случай: он даёт доступ к бакету целиком и живёт вечно.
Агентам его не выдают, для них существует `s3-gateway` с коротким сроком ссылки.

## 5. Enforcement — обязательные правила (нарушение = блокировка)

Не обходятся даже по явной просьбе пользователя. Для каждого правила —
механизм принуждения; там, где он процедурный (гейт агента, а не CI),
это указано честно — нарушение такого правила считается инцидентом.

| Правило | Технический механизм принуждения |
|---|---|
| Всё только через Dokploy API — никаких `docker run` / `docker compose up` на сервере в обход Dokploy, ни для приложений, ни для «временных» контейнеров | SSH фиксируется в `servers.md` как read-only (логи, `docker ps`, инспекция); изменяющие операции — только эндпоинты из [references/api.md](references/api.md). Если кажется, что без ручного контейнера не обойтись — стоп, вопрос пользователю |
| Домены — только через Dokploy Domains (`domain.create`), не Traefik-лейблы | перед деплоем `grep -i traefik` по compose-файлу; найдено → деплой блокируется, лейблы убрать и закоммитить |
| Секреты не попадают в git и в копии скилла | `servers.md` и creds-файлы живут только вне репозиториев (`~/.claude/nlab/` / `creds-dir`); перед любым коммитом — grep диффа на значения секретов; реальные env — только в Dokploy Environment |
| Недозаполненный env не должен молча стартовать | `${VAR:?}` в compose — деплой падает сразу и понятно (обеспечивается конвенцией `dokploy-prep`) |
| Deploy/redeploy — только после подтверждения человека | процедурный гейт: перед `compose.deploy`/`*.redeploy` показать план (сервер, проект, домены, изменения env) и получить явное подтверждение (AskUserQuestion) |
| Прод-данные не трогать: запись в прод-БД, снапшоты, удаление volume'ов | не выполнять самому — выдать команды пользователю, он запускает сам |

## 6. Процесс (шаги)

### Шаг 0: сервер и доступ

Реестр серверов — файл **`~/.claude/nlab/dokploy-servers.md`**. **В поставке скилла
его нет** — он создаётся при первом подключении сервера по шаблону
[servers.example.md](servers.example.md) и остаётся локальным.

Путь именно домашний, а не «рядом со SKILL.md»: скилл приезжает плагином, и его
папка версионная (`~/.claude/plugins/cache/nlab-vibeskills/nlab/<версия>/skills/dokploy/`).
Реестр, положенный рядом со скиллом, потеряется при первом же обновлении плагина —
вместе с API-ключами серверов. Если рядом со SKILL.md или в `~/.claude/skills/dokploy/`
нашёлся старый `servers.md` — перенеси его на канонический путь и скажи об этом
пользователю, а не заводи второй реестр. Логика:

- `servers.md` есть, пользователь назвал сервер (имя/IP/URL) → бери из реестра.
- `servers.md` есть, сервер один → используй его, упомяни в ответе какой.
- `servers.md` есть, серверов несколько, пользователь не назвал → спроси
  (AskUserQuestion, дефолтный — первый в файле).
- `servers.md` нет (первый запуск) или названного сервера в нём нет →
  **онбординг нового сервера**:
  1. Спроси у пользователя URL панели (`http://<ip>:3000` или
     `https://dokploy.example.com`) и API-токен — он берётся в
     Dokploy UI → Settings → API/CLI → Generate. Если для чтения логов
     нужен SSH-доступ — спроси и его (опционально).
  2. Проверь токен: `GET project.all` должен вернуть JSON, а не 401.
  3. Узнай GitHub-провайдер: `GET github.githubProviders` → `githubId`.
     Если пусто — скажи пользователю подключить GitHub App в Dokploy UI
     (Settings → Git), без этого деплой из приватных репо не работает.
  4. Спроси базовый домен (wildcard), указывающий на сервер, и проверь
     `dig +short <домен>` → IP сервера. Если домена нет — зафиксируй это
     в реестре: деплой возможен, но без TLS-доменов.
  5. Спроси, куда сохранять креды задеплоенных проектов (`creds-dir`);
     предложи дефолт `~/Dokploy-services`.
  6. Запиши сервер в `~/.claude/nlab/dokploy-servers.md` по шаблону
     servers.example.md (папку `~/.claude/nlab/` создай, если её нет).

**Сервер лаборатории (`dokploy.a.nlabstudio.ru`): доступ не спрашивают в чате, а
получают по заявке и читают из Vault.** Личность подтверждает GitHub, ключи никто
никому не пересылает. Порядок:

1. Токен Vault: `vault login -method=github token=$(gh auth token)` — тот же, что в
   `observability`. Не пускает — пользователь не в org `vibe-nlab`; инвайт даёт
   владелец вместе с репозиторием, дальше стоп.
2. Реквизиты — секрет `secret/users/<github-login>/dokploy` (поля `url`, `api_key`,
   `project`, `wildcard_domain`):
   ```bash
   curl -sf -H "X-Vault-Token: ${VAULT_TOKEN:-$(cat ~/.vault-token)}" \
     "https://vault.a.nlabstudio.ru/v1/secret/data/users/<github-login>/dokploy" | jq .data.data
   ```
   Нашёл — заполни из него `dokploy-servers.md` (URL, ключ, `wildcard-domain`, проект
   из поля `project`) и пользователя ни о чём не спрашивай.
3. Секрета нет (404) — подай заявку сам и подожди:
   ```bash
   gh issue create -R vibe-nlab/onboarding -t "onboard <проект>" -b ""
   ```
   Проект — имя выданного репозитория; кластер по умолчанию `agents`, иначе
   `onboard <проект> tools`. Workflow отвечает в issue за минуту — повторяй шаг 2
   до пяти минут. Заявку отклонили — причина в комментарии issue (обычно нет push
   в `sber-nlab/<проект>`): покажи её пользователю и остановись.

Ключ панели в чат не просить, свой Dokploy не поднимать. Секреты самого проекта
разработчик кладёт сам в `secret/<проект>/*` — право приходит вместе с заявкой; в env
они идут ссылками `${{vault…}}` (см. `dokploy-prep`).

Все API-вызовы дальше — `<url>/api/<endpoint>` с заголовком
`x-api-key: <api-key>` выбранного сервера. Полный справочник эндпоинтов с
проверенными payload'ами — в [references/api.md](references/api.md), читай его
перед вызовами.

### Сценарий: новый деплой

1. **Проверь входные артефакты** (п.2) и версию скилла в реестре (п.10).
2. **Пойми репозиторий** — прежде чем что-либо создавать в Dokploy: какие
   процессы/сервисы, какая БД, есть ли Dockerfile и `docker-compose.dokploy.yml`,
   есть ли деплой-доки (`DEPLOY*.md`, `.env*.example`), где healthcheck'и.
   Проверь, что код запушен и что GitHub-провайдер сервера видит репо
   (`GET github.getGithubRepositories?githubId=...`).
3. **Приведи compose к конвенциям** (п.4/п.5). Правки коммить и пушь.
   Если репо к Dokploy не готов — сначала подготовка (см. таблицу входов).
4. **DNS**: `dig +short <каждый домен>` → IP выбранного сервера.
5. **Секреты**: сгенерируй, собери блок env из `.env*.example`.
6. **Создай в Dokploy** (порядок и payload'ы — в references/api.md):
   выбери проект-кластер (`project.all` → `environmentId` окружения
   `production`; `project.create` только если кластера ещё нет) →
   `compose.create` (или `application.create` для сервиса из одного
   Dockerfile) → `compose.update` / `application.update` (источник GitHub +
   env) → секретные файлы (keys.yaml и т.п.) через `mounts.create` **до**
   первого деплоя (маунт, созданный после, попадёт в контейнер только
   следующим деплоем) → `domain.create` на каждый домен.
7. **Сохрани креды** в `<creds-dir>/<проект>-creds.md`.
8. **Подтверждение** (enforcement, п.5) → **Deploy**: `compose.deploy`,
   следи за статусом.
9. **Проверка**: `curl` по каждому домену — health-эндпоинты, HTTP→HTTPS
   редирект, тело healthz.
10. **Зафиксируй результат**: запись в `EVIDENCE.md` и `NOTES.md` проекта
    (п.8), закоммить, отчёт пользователю таблицей.

### Сценарий: эксплуатация

Сначала найди сервис: `project.all` даёт дерево проектов с
composeId/applicationId и статусами. Если непонятно, на каком сервере живёт
сервис, — пройдись `project.all` по всем серверам из реестра.

- **Redeploy** (подтянуть новый код): `compose.redeploy` / `application.redeploy`
  (с подтверждением, п.5). Дальше как в деплое: статус + health-проверка.
- **Обновить env**: `compose.update` с полем `env` (полный блок, не диф) →
  redeploy. Перед записью прочитай текущий env через `compose.one` — не потеряй
  чужие переменные.
- **Логи деплоя**: `deployment.allByCompose?composeId=...` — список деплоев со
  статусами; если деплой упал, читай его лог (см. references/api.md).
- **Логи рантайма**: по SSH read-only (адрес — в servers.md):
  `docker ps --filter name=<appName>`, `docker logs --tail 200 <container>`.
  `appName` сервиса даёт `compose.one`. Если SSH для сервера не записан —
  через API: `deployment.allByCompose` → `deployment.readLogs` (лог сборки и
  `docker compose up`), `docker.getContainers` (состояние контейнеров);
  stdout контейнера API не отдаёт — воспроизводи локально.
- **Диагностика упавшего сервиса**, типовой порядок: `composeStatus` →
  логи последнего деплоя (ошибка сборки?) → `docker ps -a` + `docker logs`
  (падает контейнер?) → healthcheck внутри контейнера → env (чего-то не
  хватает?). Частые причины из практики: незаданная обязательная env-переменная
  (`${VAR:?}` роняет compose), миграция упала (сервисы с
  `depends_on: service_completed_successfully` не стартуют), DNS не указывает
  на сервер (нет TLS). Если деплой завис/отменился без ошибки в логе — проверь
  память сервера (`free -m`, `dmesg | grep -i oom`): на малых VPS сборку
  убивает OOM-killer, помогает swap. Ещё две причины из практики: Docker
  исчерпал пулы подсетей («all predefined address pools have been fully
  subnetted» — на сервере слишком много compose-сетей, лечится только
  владельцем через `default-address-pools` в daemon.json) и домен
  отвечает 404 с сертификатом `TRAEFIK DEFAULT CERT` — Traefik не видит
  здоровый контейнер: сервис в рестарт-цикле или не прошёл healthcheck
  (`docker.getContainers`). 404 с **валидным** сертификатом — наоборот:
  роутинг работает, а у приложения нет маршрута `/` — проверяй health-эндпоинт
  из `DEPLOY_DOKPLOY.md`, не корень (так выглядели `rag.a` и `s3gate.a`).
- **Домены**: посмотреть — `domain.byComposeId`; добавить/изменить —
  `domain.create` / `domain.update`. Только так, не лейблами (п.5).

## 7. Уровень автономии и обоснование

`autonomy_level: R2` — деплой трогает прод и труднообратим. По шагам:

| Шаги | Уровень | Почему |
|---|---|---|
| Чтение: логи, статусы, диагностика, `project.all` | R4 | полностью обратимо |
| Правки compose/доков в репо (коммит в ветку) | R3 | обратимо через git |
| `compose.deploy` / `redeploy`, изменение env и доменов | R2 | прод; обязательное подтверждение человека (п.5) |
| Запись в прод-БД, снапшоты, удаление volume'ов | R0–R1 | необратимо; команды выполняет пользователь сам |

## 8. Логирование и аудит

После каждого деплоя/redeploy — append-only запись в `EVIDENCE.md` проекта
(не переписывать старые записи):

- дата, сервер, проект, commit SHA, ветка;
- домены и результаты health-проверки (URL → HTTP-код, тело healthz);
- изменения env/доменов (имена переменных, не значения секретов);
- где лежит creds-файл;
- отметка, выполнялась ли проверка версии скилла (п.10).

Решения и грабли — дописать в `NOTES.md` проекта.

## 9. Передача следующему скиллу (Handoff)

Deploy — конец цепочки Golden Path; дальше — эксплуатация этим же скиллом.
За пользователем остаётся то, что нельзя сгенерировать: внешние ключи
(LLM-провайдеры и т.п.), прод-данные, DNS у регистратора. Явно перечисли
это в финальном отчёте.

## 10. Авто-обновление

`update_check: pre_deploy` — перед каждым необратимым действием
(`compose.deploy`/`redeploy`) сверяй локальную `version` с реестром
`registry_url` (деплой-скилл enforcement-тяжёлый, устаревшее правило дороже
лишней проверки):

| Разница версий | Действие |
|---|---|
| Совпадает | работать дальше молча |
| Патч/минорная | подтянуть автоматически + одна строка уведомления |
| Мажорная | не обновлять, спросить подтверждение — возможны ломающие изменения |
| Реестр недоступен | работать на локальной версии, отметить в `EVIDENCE.md`: «проверка обновления не выполнена» |

**Обратная связь в реестр.** Наткнулся на то, чего в скилле нет или что в нём
неверно — API отвечает не так, как описано, шаг не проходит, нашлась грабля,
есть что улучшить — не молчи и не правь локальную копию: заведи issue в реестре
и продолжай работу обходным путём. Сначала поищи существующее
(`gh issue list -R vibe-nlab/nlab-vibeskills -S "<ключевые слова>"`), одна
проблема — одно issue:

```bash
gh issue create -R vibe-nlab/nlab-vibeskills -l skill-feedback \
  -t "<скилл> <версия>: <суть в одну строку>" \
  -b "<что ожидал; что произошло (ошибка дословно); как воспроизвести; предложение>"
```

Без секретов и содержимого чужих проектов. Ссылку на issue запиши в `NOTES.md`
проекта и одной строкой скажи пользователю. Нет `gh` — сформулируй текст issue
пользователю, пусть заведёт сам.

## 11. Пример (вход → выход)

**Вход**: репо `github.com/acme/notes-api` (web + postgres,
`docker-compose.dokploy.yml` от `/nlab:dokploy-prep`, код запушен), сервер

**Выход**: проект `notes-api` в Dokploy; домен `notes.example.ru` →

`OPENAI_API_KEY` он вносит сам.
