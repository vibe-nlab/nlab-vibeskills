# Dokploy: деплой и эксплуатация

## 1. Назначение (Purpose)

Завершающий скилл Golden Path (`Discovery → Design → Prep → Deploy`):
берёт подготовленный скиллом `dokploy-prep` репозиторий и разворачивает его
на Dokploy-сервере через Dokploy API, а дальше сопровождает сервис
(redeploy, логи, env, домены, диагностика). Ты — деплой-агент: всё делаешь
сам через API, у пользователя спрашиваешь только то, что реально за ним:
доступы к серверу (при первом подключении), выбор сервера/домена, решения
по прод-данным.

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Не начинай деплой, если обязательный вход отсутствует, — не «додумывай»
пропущенный шаг, а явно скажи, чего не хватает, и остановись.

| Артефакт | Обязателен? | Кто предоставляет | Если отсутствует |
|---|---|---|---|
| Репозиторий на GitHub, код запушен (`git status`, `git rev-parse HEAD origin/<branch>`) | да | пользователь | остановиться, попросить запушить — Dokploy тянет из GitHub, локальные правки не попадут |
| Для проектов компании: репозиторий — выданный централизованно (см. project_setup_best_practices.md п.5: создаёт ответственный по запросу в Telegram) | да — для Golden-Path-проектов | ответственные @sanchezgl / @KirillBorovkov | остановиться, попросить пользователя запросить репо и передать свой GitHub-никнейм; свой репозиторий не создавать |
| `docker-compose.dokploy.yml` + `.env.dokploy.example` + `DEPLOY_DOKPLOY.md` | да (для нового деплоя) | скилл `dokploy-prep` | запустить `/nlab:dokploy-prep`, если установлен; иначе подготовить самому по его конвенциям, закоммитить — и только потом продолжать |
| `servers.md` (реестр серверов, см. п.6 Шаг 0) | да | этот скилл (онбординг) | провести онбординг сервера — Шаг 0 |
| `EVIDENCE.md` проекта | да — для проектов, ведущихся по Golden Path | скилл Prep | остановиться и предупредить: деплой без evidence — отклонение от процесса, нужен явный ОК пользователя; ОК зафиксировать в `EVIDENCE.md` |

Для эксплуатации уже задеплоенного сервиса (redeploy, логи, диагностика,
env, домены) обязателен только `servers.md`.

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| Развёрнутый/обновлённый сервис | да | URL'ы, прошедшие health-проверку | пользователь |
| `<creds-dir из servers.md>/<проект>-creds.md` | да (новый деплой) | сервер, URL'ы, логины/пароли/ключи, projectId/composeId, репо/ветка/compose path | будущая эксплуатация |
| Запись в `EVIDENCE.md` проекта | да | append-only, см. п.8 | аудит, следующие сессии |
| Запись в `NOTES.md` проекта | да | что сделано, какие решения приняты и почему | любой следующий агент |
| Отчёт пользователю | да | таблица: сервер, домены, статусы, где креды, что осталось за пользователем | пользователь |

Правки репозитория (compose, доки) — закоммичены и запушены **до** деплоя.
Креды и `servers.md` в git не попадают никогда (см. п.5).

## 4. Guidance — рекомендации

- **Конвенции compose-файла** (`docker-compose.dokploy.yml`): без
  Traefik-лейблов и без проброса портов на хост (TLS и роутинг делает
  Traefik Dokploy через доменные записи); веб-сервисы — во внешней сети
  `dokploy-network` (`external: true`) **и** во внутренней сети для БД;
  БД — только во внутренней сети; данные — в named volumes; секреты и
  домены — через `${...}` из Environment сервиса. Полные правила — в скилле
  `dokploy-prep`.
- Поддомены бери от wildcard-домена сервера (из `servers.md`), если
  пользователь не дал свои.
- Секреты генерируй свежие (`python3 -c "import os,base64,secrets,string; ..."`) —
  не копируй с dev.
- Статус деплоя отслеживай поллингом `compose.one` → `composeStatus`
  (`running` → `done`/`error`), интервал 15 секунд.
- Пиши по-русски; после любой операции — короткий итог таблицей.

## 5. Enforcement — обязательные правила (нарушение = блокировка)

Не обходятся даже по явной просьбе пользователя. Для каждого правила —
механизм принуждения; там, где он процедурный (гейт агента, а не CI),
это указано честно — нарушение такого правила считается инцидентом.

| Правило | Технический механизм принуждения |
|---|---|
| Всё только через Dokploy API — никаких `docker run` / `docker compose up` на сервере в обход Dokploy, ни для приложений, ни для «временных» контейнеров | SSH фиксируется в `servers.md` как read-only (логи, `docker ps`, инспекция); изменяющие операции — только эндпоинты из [references/api.md](references/api.md). Если кажется, что без ручного контейнера не обойтись — стоп, вопрос пользователю |
| Домены — только через Dokploy Domains (`domain.create`), не Traefik-лейблы | перед деплоем `grep -i traefik` по compose-файлу; найдено → деплой блокируется, лейблы убрать и закоммитить |
| Секреты не попадают в git и в копии скилла | `servers.md` и creds-файлы живут только вне репозиториев (папка скилла / `creds-dir`); перед любым коммитом — grep диффа на значения секретов; реальные env — только в Dokploy Environment |
| Недозаполненный env не должен молча стартовать | `${VAR:?}` в compose — деплой падает сразу и понятно (обеспечивается конвенцией `dokploy-prep`) |
| Deploy/redeploy — только после подтверждения человека | процедурный гейт: перед `compose.deploy`/`*.redeploy` показать план (сервер, проект, домены, изменения env) и получить явное подтверждение (AskUserQuestion) |
| Прод-данные не трогать: запись в прод-БД, снапшоты, удаление volume'ов | не выполнять самому — выдать команды пользователю, он запускает сам |

## 6. Процесс (шаги)

### Шаг 0: сервер и доступ

Реестр серверов — файл `servers.md` рядом с этим SKILL.md. **В поставке скилла
его нет** — он создаётся при первом подключении сервера по шаблону
[servers.example.md](servers.example.md) и остаётся локальным. Логика:

- `servers.md` есть, пользователь назвал сервер (имя/IP/URL) → бери из реестра.
- `servers.md` есть, сервер один → используй его, упомяни в ответе какой.
- `servers.md` есть, серверов несколько, пользователь не назвал → спроси
  (AskUserQuestion, дефолтный — первый в файле).
- `servers.md` нет (первый запуск) или названного сервера в нём нет →
  **онбординг нового сервера**:
  1. Спроси у пользователя URL панели (`http://<ip>:3000` или
     `https://dokploy.example.com`) и API-токен — он берётся в
     Dokploy UI → Settings → API/CLI → Generate. Если для чтения логов
     нужен SSH-доступ — спроси и его (опционально).
  2. Проверь токен: `GET project.all` должен вернуть JSON, а не 401.
  3. Узнай GitHub-провайдер: `GET github.githubProviders` → `githubId`.
     Если пусто — скажи пользователю подключить GitHub App в Dokploy UI
     (Settings → Git), без этого деплой из приватных репо не работает.
  4. Спроси базовый домен (wildcard), указывающий на сервер, и проверь
     `dig +short <домен>` → IP сервера. Если домена нет — зафиксируй это
     в реестре: деплой возможен, но без TLS-доменов.
  5. Спроси, куда сохранять креды задеплоенных проектов (`creds-dir`);
     предложи дефолт `~/Dokploy-services`.
  6. Запиши сервер в `servers.md` по шаблону servers.example.md.

Все API-вызовы дальше — `<url>/api/<endpoint>` с заголовком
`x-api-key: <api-key>` выбранного сервера. Полный справочник эндпоинтов с
проверенными payload'ами — в [references/api.md](references/api.md), читай его
перед вызовами.

### Сценарий: новый деплой

1. **Проверь входные артефакты** (п.2) и версию скилла в реестре (п.10).
2. **Пойми репозиторий** — прежде чем что-либо создавать в Dokploy: какие
   процессы/сервисы, какая БД, есть ли Dockerfile и `docker-compose.dokploy.yml`,
   есть ли деплой-доки (`DEPLOY*.md`, `.env*.example`), где healthcheck'и.
   Проверь, что код запушен и что GitHub-провайдер сервера видит репо
   (`GET github.getGithubRepositories?githubId=...`).
3. **Приведи compose к конвенциям** (п.4/п.5). Правки коммить и пушь.
   Если репо к Dokploy не готов — сначала подготовка (см. таблицу входов).
4. **DNS**: `dig +short <каждый домен>` → IP выбранного сервера.
5. **Секреты**: сгенерируй, собери блок env из `.env*.example`.
6. **Создай в Dokploy** (порядок и payload'ы — в references/api.md):
   `project.create` → взять `environmentId` → `compose.create` →
   `compose.update` (источник GitHub + env) → `domain.create` на каждый домен.
7. **Сохрани креды** в `<creds-dir>/<проект>-creds.md`.
8. **Подтверждение** (enforcement, п.5) → **Deploy**: `compose.deploy`,
   следи за статусом.
9. **Проверка**: `curl` по каждому домену — health-эндпоинты, HTTP→HTTPS
   редирект, тело healthz.
10. **Зафиксируй результат**: запись в `EVIDENCE.md` и `NOTES.md` проекта
    (п.8), закоммить, отчёт пользователю таблицей.

### Сценарий: эксплуатация

Сначала найди сервис: `project.all` даёт дерево проектов с
composeId/applicationId и статусами. Если непонятно, на каком сервере живёт
сервис, — пройдись `project.all` по всем серверам из реестра.

- **Redeploy** (подтянуть новый код): `compose.redeploy` / `application.redeploy`
  (с подтверждением, п.5). Дальше как в деплое: статус + health-проверка.
- **Обновить env**: `compose.update` с полем `env` (полный блок, не диф) →
  redeploy. Перед записью прочитай текущий env через `compose.one` — не потеряй
  чужие переменные.
- **Логи деплоя**: `deployment.allByCompose?composeId=...` — список деплоев со
  статусами; если деплой упал, читай его лог (см. references/api.md).
- **Логи рантайма**: по SSH read-only (адрес — в servers.md):
  `docker ps --filter name=<appName>`, `docker logs --tail 200 <container>`.
  `appName` сервиса даёт `compose.one`. Если SSH для сервера не записан —
  ограничься логами деплоя через API.
- **Диагностика упавшего сервиса**, типовой порядок: `composeStatus` →
  логи последнего деплоя (ошибка сборки?) → `docker ps -a` + `docker logs`
  (падает контейнер?) → healthcheck внутри контейнера → env (чего-то не
  хватает?). Частые причины из практики: незаданная обязательная env-переменная
  (`${VAR:?}` роняет compose), миграция упала (сервисы с
  `depends_on: service_completed_successfully` не стартуют), DNS не указывает
  на сервер (нет TLS). Если деплой завис/отменился без ошибки в логе — проверь
  память сервера (`free -m`, `dmesg | grep -i oom`): на малых VPS сборку
  убивает OOM-killer, помогает swap.
- **Домены**: посмотреть — `domain.byComposeId`; добавить/изменить —
  `domain.create` / `domain.update`. Только так, не лейблами (п.5).

## 7. Уровень автономии и обоснование

`autonomy_level: R2` — деплой трогает прод и труднообратим. По шагам:

| Шаги | Уровень | Почему |
|---|---|---|
| Чтение: логи, статусы, диагностика, `project.all` | R4 | полностью обратимо |
| Правки compose/доков в репо (коммит в ветку) | R3 | обратимо через git |
| `compose.deploy` / `redeploy`, изменение env и доменов | R2 | прод; обязательное подтверждение человека (п.5) |
| Запись в прод-БД, снапшоты, удаление volume'ов | R0–R1 | необратимо; команды выполняет пользователь сам |

## 8. Логирование и аудит

После каждого деплоя/redeploy — append-only запись в `EVIDENCE.md` проекта
(не переписывать старые записи):

- дата, сервер, проект, commit SHA, ветка;
- домены и результаты health-проверки (URL → HTTP-код, тело healthz);
- изменения env/доменов (имена переменных, не значения секретов);
- где лежит creds-файл;
- отметка, выполнялась ли проверка версии скилла (п.10).

Решения и грабли — дописать в `NOTES.md` проекта.

## 9. Передача следующему скиллу (Handoff)

Deploy — конец цепочки Golden Path; дальше — эксплуатация этим же скиллом.
За пользователем остаётся то, что нельзя сгенерировать: внешние ключи
(LLM-провайдеры и т.п.), прод-данные, DNS у регистратора. Явно перечисли
это в финальном отчёте.

## 10. Авто-обновление

`update_check: pre_deploy` — перед каждым необратимым действием
(`compose.deploy`/`redeploy`) сверяй локальную `version` с реестром
`registry_url` (деплой-скилл enforcement-тяжёлый, устаревшее правило дороже
лишней проверки):

| Разница версий | Действие |
|---|---|
| Совпадает | работать дальше молча |
| Патч/минорная | подтянуть автоматически + одна строка уведомления |
| Мажорная | не обновлять, спросить подтверждение — возможны ломающие изменения |
| Реестр недоступен | работать на локальной версии, отметить в `EVIDENCE.md`: «проверка обновления не выполнена» |

## 11. Пример (вход → выход)

**Вход**: репо `github.com/acme/notes-api` (web + postgres,
`docker-compose.dokploy.yml` от `/nlab:dokploy-prep`, код запушен), сервер
`ams-1` из `servers.md` с wildcard `*.example.ru`.

**Выход**: проект `notes-api` в Dokploy; домен `notes.example.ru` →
сервис `web:3000` (HTTPS, healthz 200); креды в
`~/Dokploy-services/notes-api-creds.md`; запись в `EVIDENCE.md` с SHA и
результатами `curl`; отчёт-таблица пользователю + напоминание, что
`OPENAI_API_KEY` он вносит сам.
