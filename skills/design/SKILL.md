# Design: спецификация и архитектура проекта (SDD + DDD)

## 1. Назначение (Purpose)

Превращает зафиксированное намерение в спроектированную систему: закрывает
`TODO (этап Design)` в спецификации и раскладывает бэкенд по DDD. На выходе
разработчик — человек или субагент — может начинать писать код, не
догадываясь ни о контрактах, ни о том, куда что класть.

Два разных вопроса решаются в двух разных папках:

| Папка | Отвечает на вопрос | Метод |
|---|---|---|
| `spec/` | **что** система делает: контракты, модели, инструменты, схема агентов | SDD — спецификация раньше кода |
| `arch/` | **куда** что кладём: язык домена, слои, границы, модули | DDD — по размеру задачи, не «всегда по максимуму» |

SDD и DDD не конкурируют: спецификация даёт понятия и контракты, DDD
раскладывает их по коду. Единый язык из `arch/language.md` — общий для
обоих: одно понятие называется одинаково в разговоре с заказчиком, в
спецификации и в именах классов.

Скилл опирается на документы реестра — **читай их с диска, не пересказывай
по памяти**: `${CLAUDE_PLUGIN_ROOT}/skills/start/assets/AGENTS.md` (§3 SDD,
§5 автономия, §6 обязательные файлы) и
`${CLAUDE_PLUGIN_ROOT}/skills/start/references/project_setup_best_practices.md`
(§1 состав спецификации, §3 pydantic-ai, §6 модели).

Служебные артефакты процесса лежат в `project-docs/` (создана на этапе
`/nlab:start`); в корне из документов остаётся только `AGENTS.md`. Короткие
имена в тексте — файлы оттуда, в командах путь указан полностью.

Все пути ниже — относительно каталога этого скилла:

```
SKILL_DIR = ${CLAUDE_PLUGIN_ROOT}/skills/design
├── assets/spec/schemas.md          # → project-docs/spec/schemas.md
├── assets/spec/tools.md            # → project-docs/spec/tools.md
├── assets/spec/agents.md           # → project-docs/spec/agents.md
├── assets/arch/ARCH.md             # → project-docs/arch/ARCH.md
├── assets/arch/language.md         # → project-docs/arch/language.md
└── assets/arch/adr/0000-template.md  # → project-docs/arch/adr/, шаблон
```

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Скилл **не начинает работу** без выхода `/nlab:start`. Нет входа — не
додумывать, а отправить пользователя на предыдущий этап.

| Артефакт | Обязателен? | Кто предоставляет | Что делать, если отсутствует |
|---|---|---|---|
| `project-docs/intent.md` с непустыми критериями приёмки и границами | да | `/nlab:start` | остановиться, запустить `/nlab:start` |
| `project-docs/spec/SPEC.md` со всеми разделами | да | `/nlab:start` | остановиться, запустить `/nlab:start` |
| `project-docs/feature-list.json` | да | `/nlab:start` | остановиться, запустить `/nlab:start` |
| `project-docs/NOTES.md` с зафиксированным стеком | да | `/nlab:start` | стек не выбран — вернуться на Discovery, не выбирать молча за пользователя |
| Ответы на открытые вопросы из `spec/SPEC.md` §8 | да, если вопрос влияет на контракт | пользователь | спросить прямо; без ответа не проектировать «на всякий случай», а зафиксировать развилку в ADR и взять один вариант с пометкой «решение пересматривается» |
| Доменные знания: как заказчик называет вещи | да | пользователь | спросить его словами, а не терминами; единый язык нельзя выдумать за заказчика |

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| `project-docs/spec/SPEC.md` без `TODO`, статус `design` | да | markdown: разделы §2–§4 — сводка и ссылка на детальные файлы | Prep, субагенты-исполнители |
| `project-docs/spec/schemas.md` | да | pydantic-модели, **исполняемые**; таблица точек входа; правила валидации | Prep, реализация |
| `project-docs/spec/tools.md` | да, если проект содержит агента | контракт каждого инструмента, внешние системы, обратимость, автономия | Prep, реализация |
| `project-docs/spec/agents.md` | да | mermaid-схема + таблицы; для одиночного агента — «не применимо» | Prep, реализация |
| `project-docs/arch/ARCH.md` | да | масштаб DDD, слои, порты, карта модулей, границы, данные, сквозные решения | Prep, любой новый участник |
| `project-docs/arch/language.md` | да | словарь понятий, запрещённые синонимы, слова-омонимы | все — это основа именования |
| `project-docs/arch/adr/NNNN-*.md` | да, на каждое значимое решение | ADR по шаблону: контекст, решение, альтернативы, последствия | ревью, будущие участники |
| Скелет папок бэкенда | да | `domain/`, `application/`, `infrastructure/`, `interfaces/` с `.gitkeep` | Prep |
| `project-docs/feature-list.json`, дополненный | да | у каждой подзадачи — `spec_ref` на раздел спецификации | Prep, декомпозиция на субагентов |
| Записи в `project-docs/NOTES.md` и `EVIDENCE.md` | да | append-only | аудит, Deploy |

Всё коммитится по завершении. Коммит-мессадж указывает, на основании
какого входа сделано проектирование (`intent.md` → `spec/` + `arch/`).

## 4. Guidance — рекомендации (можно проигнорировать без тех. последствий)

### Язык домена — первым, до всего остального

Единый язык заполняется **до** раскладки модулей, потому что имена в нём
становятся именами классов, таблиц и папок. Берётся из того, как говорит
заказчик, а не из того, как удобно программисту. Если заказчик называет
одно и то же двумя словами — выбрать одно, второе записать в запрещённые.
Если одно слово в двух местах значит разное — это найденная граница между
доменными областями, а не повод придумать префикс.

### DDD по размеру задачи

| Уровень | Когда применять |
|---|---|
| Слои `domain` / `application` / `infrastructure` + единый язык | **всегда**, это минимум |
| + агрегаты и репозитории | есть инварианты, которые нельзя нарушить частичной записью |
| + границы доменных областей | доменных областей больше одной; одно слово значит разное |

Полный DDD на маленьком сервисе — три слоя абстракции ради одной таблицы.
Выбранный уровень и причина — в `arch/ARCH.md` §1 и в ADR. Повышать
уровень позже дешевле, чем разбирать преждевременную конструкцию.

### Правило зависимостей

Только внутрь: `interfaces → application → domain`, `infrastructure →
domain`. Домен не знает про HTTP, БД, файлы, очереди и LLM. Внешний мир
подключается через порты: домен объявляет интерфейс, инфраструктура
реализует. Это и есть то, что делает домен тестируемым без поднятой базы и
без ключа LLM, — а не «красивая архитектура» сама по себе.

### Спецификация — исполняемая, а не описательная

Модели в `spec/schemas.md` пишутся так, чтобы их можно было запустить.
Спецификация, которая не компилируется, — это пересказ намерений. Схемы
входа/выхода и инструменты — типизированные, через pydantic-ai; API писать
по <https://ai.pydantic.dev/llms.txt>, а не по памяти.

### Решения фиксируются как ADR

Значимое решение — то, которое дорого отменить: выбор хранилища, границы
областей, синхронный или фоновый режим, где человек в контуре. Каждое —
отдельным ADR с альтернативами и последствиями. Отдельно обязателен ADR на
**любое отклонение** от дефолтов компании (стек, фронтенд-темплейт,
pydantic-ai, доступ к LLM только через API, выданный репозиторий) — с
явным согласием пользователя.

### Декомпозиция под субагентов

Проектные решения субагентам не делегируются — их принимает основная
сессия (Fable-5/Opus-5) и фиксирует в спецификации. Субагентам на
Sonnet-5 уходит реализация: одна подзадача `feature-list.json` — один
субагент, и в задаче даётся **ссылка на раздел спецификации**, а не
пересказ. Поэтому у каждой подзадачи должен появиться `spec_ref`.

### Как разговаривать с пользователем

Правила из `/nlab:start` §4 действуют и здесь — они про всю сессию, а не
про один скилл. На этом этапе особенно важно: архитектура звучит для
не-инженера как заклинание. Объясняй решения через последствия для него
(«домен не знает про базу — значит, сможем поменять хранилище, не переписав
логику»), а не через названия паттернов. Термин при первом употреблении —
одна поясняющая фраза. Не спрашивай, какой слой куда положить: это твоя
работа. Спрашивай то, чего не знаешь ты, — как называются вещи в его
предметной области.

## 5. Enforcement — обязательные правила (нарушение = блокировка)

| Правило | Технический механизм принуждения | Когда |
|---|---|---|
| Проектирование не начинается без выхода Discovery | Отсутствует `intent.md`, `spec/SPEC.md` или `feature-list.json` → скилл останавливается и отправляет на `/nlab:start` | на старте |
| Спецификация допроектирована | Проверка **H**: в `spec/` и `arch/` не осталось `TODO`. Есть — статус не переводится в `design`, handoff не отдаётся | перед handoff |
| Каждый критерий приёмки покрыт | Проверка **I**: у каждого критерия из `intent.md` есть строка в `spec/SPEC.md` §1, и каждый упомянутый `id` существует в `feature-list.json`. Непокрытый критерий → блок | перед handoff |
| Модели исполняемы | Проверка **J**: python-блоки из `spec/schemas.md` компилируются и, если зависимости установлены, импортируются. Не компилируется → это не спецификация | перед handoff |
| Домен не зависит от инфраструктуры | Проверка **K**: в `domain/` нет импортов фреймворков, драйверов БД, HTTP-клиентов и SDK. Есть — правило зависимостей нарушено, слои спроектированы неверно | перед handoff и далее при каждом коммите кода |
| Схема агентов связна | Проверка **L**: каждый узел, участвующий в стрелке, объявлен; либо явное «не применимо». Схема со ссылкой на несуществующий узел — не схема | перед handoff |
| Каждый ADR виден в архитектуре | Проверка **M**: любой файл `arch/adr/NNNN-*.md`, кроме шаблона, упомянут в `arch/ARCH.md`. Иначе решение принято и потеряно | перед handoff |
| Отклонение от дефолта компании — только с ADR и согласием | Отклонение без ADR, содержащего явное согласие пользователя, не допускается; при сомнении — считать enforcement и остановиться | всегда |

Команды проверок — выполнять как есть, результат каждой записывать в
`EVIDENCE.md` (п.8). Все запускаются из корня проекта.

```bash
# H. Спецификация и архитектура допроектированы. Ожидание: пусто.
# Строки-цитаты (`>`) исключены: пояснения в шапках шаблонов сами упоминают
# слово TODO, без фильтра проверка не обнулилась бы никогда.
grep -rn 'TODO' project-docs/spec/ project-docs/arch/ --include='*.md' | grep -vE '^[^:]+:[0-9]+:[[:space:]]*>'

# I. Покрытие критериев приёмки.
python3 - <<'PY'
import json, re, pathlib
intent = pathlib.Path("project-docs/intent.md").read_text()
block = re.search(r"##\s*Критерии приёмки\s*\n(.*?)(?=\n##\s|\Z)", intent, re.S)
crit = re.findall(r"^\s*(\d+)\.", block.group(1), re.M) if block else []
spec = pathlib.Path("project-docs/spec/SPEC.md").read_text()
rows = dict(re.findall(r"^\|\s*(\d+)\s*\|.*?\|([^|]*)\|\s*$", spec, re.M))
ids = {f["id"] for f in json.loads(pathlib.Path("project-docs/feature-list.json").read_text())}
missing = [c for c in crit if c not in rows]
refs = {r.strip(" `") for v in rows.values() for r in v.split(",") if r.strip(" `")}
unknown = sorted(refs - ids)
if not crit: print("в intent.md не найдено ни одного критерия")
if missing: print("критерии без строки в spec/SPEC.md:", ", ".join(missing))
if unknown: print("ссылки на несуществующие подзадачи:", ", ".join(unknown))
if crit and not missing and not unknown: print(f"OK: покрыто критериев {len(crit)}")
PY

# J. Модели из spec/schemas.md исполняемы.
python3 - <<'PY'
import re, pathlib, sys
code = "\n".join(re.findall(r"```python\n(.*?)```", pathlib.Path("project-docs/spec/schemas.md").read_text(), re.S))
if not code.strip():
    print("нет ни одного блока моделей"); sys.exit(1)
obj = compile(code, "project-docs/spec/schemas.md", "exec")   # синтаксис — жёстко
try:
    exec(obj, {})
    print("OK: модели исполняются")
except ImportError as e:                         # зависимостей ещё нет — не блокер
    print(f"OK синтаксис; импорт отложен до Prep ({e})")
PY

# K. Домен не зависит от инфраструктуры. Ожидание: пусто.
grep -rnE '^\s*(import|from)\s+(fastapi|starlette|flask|django|sqlalchemy|psycopg|asyncpg|redis|httpx|requests|aiohttp|boto3|openai|anthropic|pydantic_ai)\b' \
  --include='*.py' backend/domain/ 2>/dev/null

# L. Схема агентов связна.
python3 - <<'PY'
import re, pathlib, sys
t = pathlib.Path("project-docs/spec/agents.md").read_text()
m = re.search(r"```mermaid\n(.*?)```", t, re.S)
if not m:
    print("OK: схема не применима" if "не применимо" in t.lower() else "нет mermaid-блока"); sys.exit()
body = m.group(1)
declared = set(re.findall(r"^\s*(\w+)\s*[\[\(\{]", body, re.M))
src = re.findall(r"(\w+)\s*--", body)
dst = re.findall(r"--[->]*\s*(?:\|[^|]*\|)?\s*(\w+)", body)
undeclared = sorted({n for n in src + dst if n not in declared})
print("узлы без объявления:", ", ".join(undeclared)) if undeclared else print("OK: схема связна")
PY

# M. Каждый ADR упомянут в ARCH.md. Ожидание: пусто.
for f in project-docs/arch/adr/[0-9]*.md; do
  case "$f" in *0000-template.md) continue;; esac
  grep -q "$(basename "$f" .md)" project-docs/arch/ARCH.md || echo "ADR не упомянут в ARCH.md: $f"
done
```

`grep` возвращает код 1, когда совпадений нет — для H, K и M это успех.

## 6. Процесс (шаги)

1. **Проверить входы** (п.2). Нет `intent.md` / `spec/SPEC.md` /
   `feature-list.json` — остановиться и отправить на `/nlab:start`. Один
   раз за сессию сверить версию скилла с реестром (п.10).
2. **Прочитать правила и текущее состояние**: `AGENTS.md` и
   `project_setup_best_practices.md` из реестра, затем `intent.md`,
   `spec/SPEC.md` (что уже заполнено, что помечено `TODO`), `NOTES.md`
   (какой стек зафиксирован), `feature-list.json`.
3. **Собрать единый язык** — `arch/language.md`. Спрашивать пользователя
   его словами: как называется эта штука, чем отличается от той, называют
   ли это где-то иначе. Заполнить словарь, запрещённые синонимы и
   слова-омонимы. **Это шаг до всей остальной архитектуры.**
4. **Выбрать масштаб DDD** (п.4) и записать выбор с обоснованием в
   `arch/ARCH.md` §1 и отдельным ADR. По умолчанию — слои и единый язык;
   границы областей выделять, только если нашлись слова-омонимы или
   несколько доменных областей.
5. **Закрыть спецификацию**: скопировать шаблоны из `$SKILL_DIR/assets/spec/`
   и заполнить — `schemas.md` (модели вход/выход, правила валидации),
   `tools.md` (контракт каждого инструмента, внешние системы, обратимость,
   автономия), `agents.md` (mermaid-схема, что передаётся, где человек в
   контуре, отказы и повторы). В `spec/SPEC.md` §2–§4 оставить короткую
   сводку и ссылку на детальный файл, снять `TODO`, перевести статус в
   `design`, добавить строку в журнал изменений.
6. **Спроектировать архитектуру** — `arch/ARCH.md`: слои и что каждому
   запрещено, порты и их реализации, карта модулей, границы областей (если
   выбраны), данные и владельцы, фронтенд (если есть), сквозные решения,
   раздел «что осознанно не делаем».
7. **Создать скелет папок** бэкенда по карте модулей: `domain/`,
   `application/`, `infrastructure/`, `interfaces/` с `.gitkeep`. Код не
   писать — это работа Prep; здесь только форма.
8. **Оформить ADR** на каждое значимое решение и на каждое отклонение от
   дефолта компании (шаблон — `$SKILL_DIR/assets/arch/adr/0000-template.md`).
   Нумерация сквозная, каждый ADR упоминается в журнале `arch/ARCH.md`.
9. **Привязать подзадачи**: у каждой записи `feature-list.json` проставить
   `spec_ref` — на какой раздел спецификации она опирается. Критерий без
   подзадачи или подзадача без `spec_ref` — дыра в декомпозиции.
10. **Прогнать проверки H–M** (п.5) и записать результат каждой в
    `EVIDENCE.md` проверяемой формулировкой.
11. **Закоммитить** `spec/`, `arch/`, скелет папок и `feature-list.json`
    одним коммитом. Записать в `NOTES.md` принятые решения и почему.
12. **Отдать handoff** (п.9) человеческим языком: как система будет
    устроена и что это даёт, какие решения приняты и что они закрывают,
    что осталось открытым, и один конкретный следующий шаг.

## 7. Уровень автономии и обоснование

`autonomy_level: R3` — проектирование обратимо (черновик в ветке), но
влияет на весь проект, поэтому ревью до перехода на Prep желательно. По
шагам:

| Шаг | Обратимость | Уровень | Что это значит |
|---|---|---|---|
| Заполнение шаблонов, скелет папок, `spec_ref` | полностью обратимо | R4 | самостоятельно |
| Схемы, контракты инструментов, карта модулей | обратимо, но переделка дорожает с каждым днём | R3 | самостоятельно, показать результат до Prep |
| Выбор масштаба DDD и границ областей | переделка = переписывание кода | R2 | решение с обоснованием + ADR, озвучить пользователю |
| Выбор хранилища, внешних сервисов, где человек в контуре | влияет на деньги, данные, эксплуатацию | R2 | ADR + явное подтверждение пользователя |
| Отклонение от дефолта компании | ломает единообразие всех проектов | R1 | только по явному решению пользователя, ADR обязателен |
| Написание кода реализации | — | **не в этом скилле** | это Prep |

## 8. Логирование и аудит

В `EVIDENCE.md` — проверяемые записи, а не оценки:

- входы приняты: `intent.md`, `spec/SPEC.md`, `feature-list.json` — есть;
  критериев приёмки — N;
- единый язык: понятий — N, запрещённых синонимов — N, слов-омонимов — N;
- выбранный масштаб DDD и ADR, в котором это обосновано;
- проверка **H** — команда и результат (`TODO` не осталось);
- проверка **I** — покрыто критериев N из N; ссылки на подзадачи валидны;
- проверка **J** — модели компилируются; импорт выполнен или отложен до
  Prep (указать, какого модуля не хватило);
- проверка **K** — запрещённых импортов в `domain/` — 0;
- проверка **L** — схема связна либо «не применимо» с обоснованием;
- проверка **M** — ADR без упоминания в `ARCH.md` — 0; всего ADR — N;
- подзадач с `spec_ref` — N из N.

В `NOTES.md` — решения и обоснования: масштаб DDD, границы областей,
хранилище, где человек в контуре, каждое отклонение от дефолта компании с
пометкой «решение пользователя» и ссылкой на ADR.

## 9. Передача следующему скиллу (Handoff)

Передаётся этапу **Prep** — `/nlab:dokploy-prep`. Обязательно на выходе:
`spec/` без `TODO` со статусом `design`, `arch/ARCH.md` и
`arch/language.md`, ADR на значимые решения, скелет папок бэкенда,
`feature-list.json` с `spec_ref` у каждой подзадачи, всё закоммичено.

| Что дальше | Кто делает |
|---|---|
| Реализация по спецификации | основная сессия + субагенты на Sonnet-5, одна подзадача — один субагент со ссылкой на раздел `spec/` |
| UI по дизайн-системе NeuroLab | скилл `/nlab:design-ui` |
| Подготовка репозитория к деплою | скилл `/nlab:dokploy-prep` |
| Деплой | скилл `/nlab:dokploy` |

Prep не стартует, пока проверка **H** не пуста. Deploy не стартует с
незакрытыми блокерами из `intent.md`.

## 10. Авто-обновление

`update_check: per_session` — один раз при первом использовании скилла в
сессии сверить `version` с `registry_url`.

| Разница версий | Действие |
|---|---|
| Совпадает | Работать дальше молча |
| Патч/минорная | Сообщить одной строкой и предложить `/plugin marketplace update nlab-vibeskills` |
| Мажорная | Не работать по новым правилам без подтверждения |
| Реестр недоступен | Работать на локальной версии, отметить в `EVIDENCE.md` |

Обновление плагина выполняет пользователь — агент не может обновлять
плагины сам. Это guidance-механизм, недоступность реестра не блокирует
работу.

## 11. Примеры

**Вход** — тот же проект, что в примере `/nlab:start`: экстрактор
реквизитов договора. В `spec/SPEC.md` разделы §2–§4 помечены
`TODO (этап Design)`.

**Диалог** (спрашиваем то, чего не знает агент, — язык предметной области):
как вы называете стороны договора — «стороны», «контрагенты»,
«участники»? Сумма — это всегда одна цифра или бывает разбивка по этапам?
«Срок» — это дата окончания или период действия?

**Выход** — `arch/language.md`:

```markdown
| Понятие | Что это на языке заказчика | Имя в коде | Где живёт |
|---|---|---|---|
| Договор | загруженный PDF, из которого достаём данные | `Contract` | domain |
| Сторона | кто подписывает — заказчик и исполнитель | `Party` | domain |
| Реквизит | одно извлечённое поле с уверенностью модели | `Requisite` | domain |

## Синонимы, которые мы НЕ используем
| Сказали так | Используем | Почему |
|---|---|---|
| контрагент, участник | Сторона | заказчик чаще говорит «стороны» |
```

**Выход** — `arch/ARCH.md` §1 и §2 (фрагмент):

```markdown

Слои + единый язык. Границы областей не выделяются: доменная область одна
(разбор договора), слов-омонимов не найдено. Обоснование — ADR-0001.

## 2. Слои
| Слой | Что внутри | Что запрещено |
|---|---|---|
| `domain/` | Contract, Party, Requisite, правила валидации реквизитов | pypdf, httpx, pydantic_ai |
| `application/` | сценарий «разобрать договор»: извлечь текст → достать поля | прямые вызовы LLM |
| `infrastructure/` | PdfTextExtractor, LlmRequisiteExtractor (порт из domain) | бизнес-правила |
| `interfaces/` | POST /contracts, обработчик загрузки | бизнес-правила |

| Порт (объявлен в) | Реализация (в) | Зачем |
|---|---|---|
| `domain.ports.RequisiteExtractor` | `infrastructure.llm` | домен тестируется без ключа LLM |
```
