# Dokploy-prep: подготовка сервиса к деплою

## 1. Назначение (Purpose)

Prep-этап Golden Path: превращает работающий репозиторий в готовый к
деплою на Dokploy артефакт — три файла по конвенциям + приведённый в
порядок Dockerfile, — чтобы тот, кто хостит (человек или скилл `/nlab:dokploy`),
задеплоил без доработок и без «переводчика».

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Не начинай работу, если обязательного входа нет, — явно скажи, чего не
хватает, и остановись, а не «додумывай».

| Артефакт | Обязателен? | Кто предоставляет | Если отсутствует |
|---|---|---|---|
| Git-репозиторий с работающим приложением (собирается/запускается) | да | пользователь / предыдущие этапы | остановиться: prep не чинит приложение, сначала доведите его до рабочего состояния |
| Понимание состава: сервисы, БД, что смотрит наружу | да | код репо + ответы пользователя | извлечь из репо; развилки — спросить (п.6 шаг 2) |
| Спецификация/`intent.md` (для проектов по Golden Path) | желателен | скиллы Discovery/Design | работать по коду репо, зафиксировать предположения в `NOTES.md` как предположения |

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| `docker-compose.dokploy.yml` | да | стек для Dokploy — ровно с этим именем, его ждёт деплой как Compose Path | скилл `/nlab:dokploy` / хостящий |
| `.env.dokploy.example` | да | шаблон переменных Environment без значений секретов | хостящий |
| `DEPLOY_DOKPLOY.md` | да | короткий гайд: домен↔сервис↔порт, обязательные env, как проверить | хостящий |
| Dockerfile + `.dockerignore` | да | собирается из корня без внешних аргументов | Dokploy build |
| Запись в `EVIDENCE.md` | да | что проверено и как (п.8), append-only | скилл `/nlab:dokploy` (не стартует без evidence) |
| Git commit + push | да | всё созданное закоммичено — Dokploy тянет из GitHub | скилл `/nlab:dokploy` |

Не переиспользуй `docker-compose.yml` / `docker-compose.prod.yml` — dev- и
prod-стеки живут отдельно, Dokploy-вариант всегда свой.

## 4. Guidance — рекомендации

### Compose-файл

Шаблон с комментариями — [assets/docker-compose.dokploy.yml](assets/docker-compose.dokploy.yml).
Адаптируй его под проект, не копируй вслепую:

1. **Сети**: веб-сервисы — в `dokploy-network` (`external: true`, создана
   Dokploy) **и** во внутренней сети; БД/брокеры — только во внутренней,
   наружу не видны.
2. **Данные — в named volumes** (переживают redeploy). Bind-mount'ы на пути
   сервера не использовать.
3. **Healthcheck у каждого долгоживущего сервиса.** Для веб-приложений —
   HTTP-эндпоинт (`/healthz`, желательно с проверкой БД). Без healthcheck
   `depends_on: condition: service_healthy` не работает и 502 при старте
   неотличим от реальной поломки.
4. **Миграции — отдельным one-shot сервисом** (`restart: "no"`, `depends_on`
   БД healthy), а приложения стартуют после него через
   `condition: service_completed_successfully`. Идемпотентно.
5. **Логи ограничивай** (json-file, max-size/max-file через YAML-якорь) —
   иначе диск сервера со временем забьётся.
6. **Кросс-ссылки между сервисами** (URL друг друга для UI) собирай из
   `*_DOMAIN`-переменных, не хардкодь.

### .env.dokploy.example

Шаблон — [assets/env.dokploy.example](assets/env.dokploy.example):

- Все обязательные значения — `CHANGE_ME_...`, чтобы grep ловил незаполненное.
- К каждой переменной — комментарий: зачем она и как получить значение
  (это единственная документация, которую увидит будущий деплой).
- Домены — отдельным блоком сверху. Реальные поддомены назначает хостящий
  на своём сервере, поэтому ставь осмысленные плейсхолдеры вида
  `api.example.com` / `app.example.com` — важны имена переменных и то, какие
  сервисы вообще получают домен, а не конкретные значения.

### DEPLOY_DOKPLOY.md

Короткий файл (не роман), обязательно содержит:

- **Таблицу домен ↔ сервис в compose ↔ внутренний порт** — по ней хостящий
  заводит домены через вкладку Domains (или API Dokploy). Домены —
  плейсхолдеры, хостящий заменит на поддомены своего сервера.
- Список обязательных env-переменных и как сгенерировать секреты.
- Как проверить после деплоя (URL'ы health-эндпоинтов, ожидаемые ответы).
- Особенности проекта: сервисы, которые нельзя масштабировать; порядок
  миграций; известные грабли.

### Dockerfile и прочее

- Dockerfile должен собираться из корня репо без внешних аргументов
  (Dokploy делает простой `build: .`).
- Проверь, что в образе нет вшитых секретов и `localhost`-адресов.
- Если healthz-эндпоинта в приложении нет — добавь (это правка кода,
  согласуй с пользователем, если проект не твой).

## 5. Enforcement — обязательные правила (нарушение = блокировка)

| Правило | Технический механизм принуждения |
|---|---|
| Никаких Traefik-лейблов и никаких `ports:` наружу — TLS/роутинг делает Traefik Dokploy через вкладку Domains, вся маршрутизация видна в UI | перед коммитом `grep -iE 'traefik|^\s*ports:'` по `docker-compose.dokploy.yml`; найдено → файл не сдаётся, убрать |
| Секреты не коммитятся никогда; реальные значения генерирует и хранит хостящий | `.dockerignore` и `.gitignore` исключают `.env*` (кроме `*.example`); перед коммитом grep диффа: в example-файле только `CHANGE_ME_*`-значения |
| Обязательные env объявлены fail-loud | `${VAR:?VAR не задан в Dokploy env}` в compose — деплой с недозаполненным env падает сразу и понятно, а не молча стартует со сломанной конфигурацией |
| Compose синтаксически валиден | гейт перед коммитом: `docker compose -f docker-compose.dokploy.yml config` с фиктивными env проходит (сеть dokploy-network локально отсутствует — это ок, важны YAML и подстановки) |
| `.dockerignore` обязателен | проверка наличия и содержимого: `.git`, `.env*` (кроме `*.example`), логи, кэши, `node_modules`/`venv`, тесты — иначе секреты и мусор попадут в образ |

## 6. Процесс (шаги)

1. Проверь входные артефакты (п.2) и версию скилла в реестре (п.10).
2. Изучи репо: какие процессы/сервисы, какая БД, где конфиг, есть ли уже
   compose-файлы и Dockerfile, есть ли healthz. Составь план: сервисы →
   какие получают домен (значения — плейсхолдеры) → порты → env. Покажи
   пользователю таблицу; есть развилки — спроси.
3. Создай/приведи в порядок три файла + Dockerfile/`.dockerignore` по
   правилам (п.4–5).
4. Прогони enforcement-гейты (п.5): grep-проверки + `docker compose config`.
5. Запиши результат проверок в `EVIDENCE.md`, решения — в `NOTES.md` (п.8).
6. Закоммить и запушь; коммит-мессадж указывает, что подготовлено и чем
   проверено.
7. Финальный чеклист пользователю: что создано, таблица доменов, какие env
   обязательны — и напомни передать ссылку на репозиторий тому, кто будет
   хостить: дальше деплой на его стороне (скилл `/nlab:dokploy`).

## 7. Уровень автономии и обоснование

`autonomy_level: R3` — правки обратимы через git (ветка/PR, ревью перед
merge по желанию пользователя). Исключение: правки кода приложения
(например, добавить healthz-эндпоинт) в чужом проекте — R2, согласуй с
пользователем до внесения.

## 8. Логирование и аудит

Append-only запись в `EVIDENCE.md` (проверяемые формулировки, не «всё
хорошо»):

- дата, список созданных/изменённых файлов;
- `docker compose config` — прошёл (с какими фиктивными env);
- grep-гейты (traefik/ports, секреты, CHANGE_ME) — 0 находок;
- есть ли healthz у каждого веб-сервиса; что осталось нерешённым;
- отметка о проверке версии скилла (п.10).

Предположения, принятые без пользователя, — в `NOTES.md` как предположения.

## 9. Передача следующему скиллу (Handoff)

Передаётся скиллу **`/nlab:dokploy`** (или человеку, который хостит).
Обязательно на выходе: запушенный репозиторий с
`docker-compose.dokploy.yml`, `.env.dokploy.example`, `DEPLOY_DOKPLOY.md`
и записью в `EVIDENCE.md` — без неё деплой-скилл не стартует.

## 10. Авто-обновление

`update_check: per_session` — при первом использовании скилла в сессии
сверь локальную `version` с реестром `registry_url`:

| Разница версий | Действие |
|---|---|
| Совпадает | работать дальше молча |
| Патч/минорная | подтянуть автоматически + одна строка уведомления |
| Мажорная | не обновлять, спросить подтверждение — возможны ломающие изменения |
| Реестр недоступен | работать на локальной версии, отметить в `EVIDENCE.md`: «проверка обновления не выполнена» |

## 11. Пример (вход → выход)

**Вход**: репо FastAPI-сервиса `notes-api` (uvicorn + Postgres + Alembic),
Dockerfile есть, compose-файлов для прода нет.

**Выход**: `docker-compose.dokploy.yml` (web в `dokploy-network` +
internal, postgres только internal, one-shot `migrate`, healthcheck на
`/healthz`, логи ограничены); `.env.dokploy.example`
(`NOTES_DOMAIN=api.example.com`, `POSTGRES_PASSWORD=CHANGE_ME_...` с
комментариями); `DEPLOY_DOKPLOY.md` с таблицей `api.example.com ↔ web ↔
8000`; `.dockerignore`; запись в `EVIDENCE.md` («compose config — ок,
grep-гейты — 0 находок»); всё закоммичено и запушено.
