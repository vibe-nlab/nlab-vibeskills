# Observability: трейсинг агентов в общий MLflow

## 1. Назначение (Purpose)

Подключает проект к обсервабилити компании: каждый запуск агента пишется
трейсом в общий MLflow Tracking Server — видно, какой промпт ушёл, что
передано, какие LLM-/tool-/MCP-вызовы случились внутри и что вернулось,
сколько токенов потрачено. Один сервер на компанию, один experiment на
проект. Интеграция — тонкая: одна env-переменная и один модуль
`tracing.py`; без адреса сервера трейсинг молча выключен.

## 4. Guidance — рекомендации

- **API не по памяти.** Перед написанием кода сверь актуальный API:
  интеграция MLflow×PydanticAI —
  <https://mlflow.org/docs/latest/genai/tracing/integrations/listing/pydantic_ai/>,
  дока pydantic-ai — <https://ai.pydantic.dev/llms.txt> (домен переехал на
  <https://pydantic.dev/docs/ai/llms.txt>).
- **⚠️ Флейвор `mlflow.pydantic_ai` написан под pydantic-ai 1.x — на 2.x он
  ломает КАЖДОЕ создание агента.** Дока MLflow предлагает
  `Agent("model", instrument=True)`, и флейвор ровно этот аргумент подставляет
  в `Agent.__init__` патчем. В pydantic-ai 2.x аргумент из конструктора убрали —
  он переехал в `Agent.instrument_all()`. Коварство в том, что `autolog()`
  отрабатывает молча и успешно, а `TypeError` вылезает позже, на каждом вызове
  агента. **Поэтому после `autolog()` обязательна проба пробным агентом** —
  шаблон `assets/tracing.py` её делает; не выбрасывай её при адаптации.
  Проверено на mlflow 3.15.1 + pydantic-ai 2.23.0, 2026-08-04.
- **Рабочий путь для pydantic-ai 2.x — нативная OTel-инструментация через мост
  MLflow:** `Agent.instrument_all(InstrumentationSettings(tracer_provider=
  mlflow.tracing.get_bridged_tracer_provider(), include_content=True))`. Мост
  существует ровно для этого. Спаны выходят богаче флейвора: `invoke_agent`
  типа AGENT с вложенным CHAT_MODEL и атрибутами `gen_ai.*` (модель, провайдер,
  токены, сообщения) по семантическим конвенциям OTel. Это **не** отклонение от
  дефолта компании — тот же MLflow, другой способ отдать ему спаны.
- **Спаны шагов и спаны агента должны попасть в ОДИН трейс.** Без
  `MLFLOW_TRACE_PROPAGATE_TO_OTEL_CONTEXT=True` инструментация pydantic-ai не
  видит родителя из `mlflow.start_span()` и уезжает отдельным трейсом: в UI два
  несвязанных дерева на один шаг, а тег сессии остаётся на пустом. Переменная
  читается при инициализации провайдера, поэтому выставляется ДО первого
  обращения к mlflow (в шаблоне — в начале `setup_tracing()`).
- **Experiment = имя проекта** (имя выданного репозитория). Один проект —
  один experiment, не плоди experiment'ы на окружения: dev/prod различай
  тегом, если понадобится.
- **Что попадает в трейс само** (autolog): промпты и сообщения, вызовы LLM
  (модель, параметры, ответ, токены), вызовы tools и MCP-серверов,
  streaming, structured output, ошибки и латентность. Руками дологировать
  нужно только то, что снаружи агента.
- **Один запуск — один трейс.** Многошаговая система (конвейер, мультиагентная
  связка, диалог) оборачивается корневым спаном `run_span()` в точке входа, а
  каждый шаг — `step_span()` внутри него. Без корневого спана каждый шаг
  становится КОРНЕМ собственного трейса: в UI N несвязанных деревьев вместо
  одного, и структура — последовательность, веер параллельных шагов, слияние
  обратно — не видна вообще. Параллельные шаги наследуют контекст сами:
  `asyncio` копирует contextvars при создании задачи. Проверяется просто:
  трейсов на один запуск должно быть **ровно один**.
- **Под каким именем агент виден в трейсе.** Имя собирается лестницей, и каждая
  ступень задаётся в своём месте — проверь все, иначе в UI будет «agent» и
  безымянные спаны:

  | Ступень | Что видно в MLflow | Откуда берётся |
  |---|---|---|
  | эксперимент | `notes-agent` | `MLFLOW_EXPERIMENT` в env; по конвенции — имя выданного репозитория |
  | корневой спан | `run 20260804-142118` | `run_span(name=...)` |
  | спан шага | `10_extract` | `step_span(name=...)` |
  | **спан агента** | `invoke_agent 10_extract` | **`Agent(name=...)` в pydantic-ai** |
  | спан вызова модели | `chat claude-sonnet-4-6` | id модели, проставляется сам |

  Ключевое: **`Agent(name=...)` — единственный источник имени агента**. Не задашь —
  получишь `invoke_agent agent` у всех агентов сразу, и в трейсе будет не отличить
  один шаг от другого (проверено на pydantic-ai 2.23). Если агент создаётся
  на каждый вызов, передавай туда имя шага — тогда имя шага и имя агента совпадут,
  и дерево читается без расшифровки.
- **Системный промпт, вход и ответ шага кладите в `inputs`/`outputs` спана шага —
  и НЕ через `Agent(system_prompt=…)`.** Без этого в трейсе видно только сообщение
  пользователя и ответ модели: промпт уезжает в атрибут `gen_ai.system_instructions`,
  куда никто не смотрит, — а именно он объясняет, ПОЧЕМУ шаг ответил так, а не иначе.
  Очевидный ход — передать промпт через `Agent(system_prompt=…)`, чтобы он лёг в
  сообщения и отрисовался в чат-виде, — **ломает трейсинг**: главный трейс
  многошагового запуска перестаёт экспортироваться вовсе, доезжают только фоновые
  трейсы, дерево пропадает. Ошибок при этом никаких, все POST 200. Через `inputs`
  спана те же 32 КБ промпта уезжают нормально: дело не в объёме, а в сериализации
  сообщений агента. Бонус — MLflow подставляет вход и выход спана в колонки
  Request/Response списка трейсов, и прямо в списке видно, с каким промптом шаг
  работал и что ответил. Проверено на 16-шаговом конвейере, mlflow 3.15.1 +
  pydantic-ai 2.23.
- **Фоновые задачи запускай СНАРУЖИ корневого спана.** Задача, созданная внутри
  `run_span()`, наследует контекст с корневым спаном; к моменту её работы он уже
  закрыт, и MLflow её спаны **молча отбрасывает** — в трейсе остаётся только спан
  агента, без имени шага и с чужой сессией. Хуже того, поведение
  **недетерминированное**: успела задача стартовать до закрытия корня — попадёт
  внутрь, не успела — уедет отдельно. На медленном прогоне часть задач попадала
  внутрь, на быстром ни одна. Правило: всё, что «фоном после основной работы»
  (дайджесты, постобработка, отправка уведомлений), запускается за пределами
  `with run_span(...)`. Тогда контекст чистый и каждая задача даёт свой аккуратный
  трейс со своей сессией.
- **Сессию ставь атрибутом `session.id` на корневом спане, а не только
  метаданными.** MLflow при сохранении трейса выводит сессию из атрибутов спанов:
  `session.id`, а если его нет — `gen_ai.conversation.id`. Второй ставит сам
  pydantic-ai, свой UUID на каждый запуск агента, и он **перебивает**
  `update_current_trace(metadata={"mlflow.trace.session": …})`. Симптом: в UI
  сессия запуска — «019fcce6-…», найти запуск по своему id нельзя. `session.id`
  проверяется первым и выигрывает. Проверено на mlflow 3.15.1 + pydantic-ai 2.23
  (`store/tracking/sqlalchemy_store.py`).
- **Корневой спан обязан нести вход и выход.** MLflow строит превью строки в
  списке трейсов (`request_preview` / `response_preview`) именно из входа и
  выхода КОРНЕВОГО спана. Оставить их пустыми — получить список одинаковых
  безликих строк: видно, что запуски были, и ничего больше. На вход кладите то,
  по чему запуск узнаётся (что подали, какого типа, ключевые поля контекста), на
  выход — исход (результат, статус, ошибку). Выход ставьте в `finally`:
  оборванный запуск обязан быть отличим от успешного. Тип корня — `SpanType.CHAIN`,
  а не дефолтный `UNKNOWN`: по типу UI рисует иконку и группирует спаны.
  Важно: **задним числом это не чинится** — трейс пишется один раз, у клиента
  MLflow есть только теги (`set_trace_tag`), менять спаны завершённого трейса
  нельзя. Не заполнили сразу — перезапускайте прогон.
- **Спан не должен подменять собой ошибку кода.** Обычный способ «сделать
  обсервабилити безопасной» — обернуть весь блок со спаном в `try/except` — на
  контекст-менеджере даёт обратный эффект. `@contextmanager` бросает исключение
  тела ВНУТРЬ генератора, в точку `yield`: в такой `except` прилетает не сбой
  mlflow, а штатная ошибка шага. Её глотают, генератор доходит до второго
  `yield`, и наружу вместо неё летит `RuntimeError: generator didn't stop after
  throw()` — настоящая ошибка потеряна, в логе враньё про «сбой трейсинга», в
  трейсе шаг не помечен упавшим. Правильно: `yield` тела вне `except`, спан
  закрывается руками (`_quiet_span` в шаблоне) — сбой трейсинга в лог, ошибка
  шага наружу без изменений. Гейт — в п.5.
- **Юзер-инпуты и сессии.** Всё, что прилетает в API до агента, привязывай
  к трейсу тегами `mlflow.trace.session` / `mlflow.trace.user` — хелпер
  `tag_current_trace()` в шаблоне; вызывай в обработчике запроса (или
  FastAPI-middleware), где известны session_id/user_id.
- **Chain-of-thought — с оговоркой:** reasoning-контент попадает в трейс,
  только если модель возвращает его через API. Через гейт
  `ai.nlabstudio.ru` это зависит от модели — проверь на живом ключе и
  зафиксируй результат в `NOTES.md`, а не обещай пользователю «весь CoT».
- **Локальная проверка без общего сервера:** подними `mlflow server` /
  `mlflow ui` на localhost, укажи его в `MLFLOW_TRACKING_URI`, прогони один
  вызов агента и посмотри трейс — так интеграция проверяется ещё до того,
  как появится общий сервер. В коммит локальный адрес не тащи.
- **Проверяй трейсинг бесплатно — заглушкой роутера, а не подменой модели.**
  Полный прогон многошагового агента стоит сотни тысяч входных токенов, причём
  основная часть — не пользовательский ввод, а знания в промптах шагов; коротким
  входом это не срезать. Для проверки инфраструктуры живая модель не нужна.
  Готовая заглушка — [assets/fake_llm_router.py](assets/fake_llm_router.py):
  OpenAI-совместимый `/v1/chat/completions` с поддельными ответами, ответы под
  свой проект правятся в одной функции.

  **Почему именно заглушка сети, а не `TestModel`/`FunctionModel`.** Подмена модели
  выбрасывает весь боевой путь: OpenAI-SDK, HTTP, `OpenAIChatModel` и его
  инструментацию — а баги трейсинга живут именно там. Проверено на живом проекте:
  перетирание сессии через `gen_ai.conversation.id` на `FunctionModel` **не
  воспроизводилось**, а на заглушке — воспроизвелось сразу, вместе с ещё одним
  дефектом (фоновые задачи вне трейса). Заглушка подменяет только сеть, всё выше по
  стеку остаётся настоящим.
- **Langfuse и прочие бэкенды трейсинга** — осознанные альтернативы, но
  **дефолт компании — MLflow**; отклонение только решением пользователя с
  записью в `NOTES.md`. Нативная OTel-инструментация pydantic-ai альтернативой
  MLflow не является: через мост выше она пишет ровно в MLflow.

## 5. Enforcement — обязательные правила (нарушение = блокировка)

| Правило | Технический механизм принуждения |
|---|---|
| Адрес сервера и креды — только через env, не в коде и не в репо | перед коммитом `grep -rE "MLFLOW_TRACKING_URI.{0,10}=.{0,10}https?" --include='*.py' backend/` → 0 находок; в `.env*.example` значение пустое или `CHANGE_ME_*` |
| Пустой/отсутствующий `MLFLOW_TRACKING_URI` не ломает приложение | обязательный прогон перед сдачей: старт приложения и один вызов агента **без** переменной; падение → блокер, чинить до сдачи |
| Обсервабилити не роняет прод | `setup_tracing()`/`tag_current_trace()` в шаблоне глотают свои исключения (try/except + лог) — при адаптации шаблона это не вырезать |
| Спан не подменяет собой ошибку кода | прогон перед сдачей: шаг, который штатно падает (`raise ValueError("проба")`), с ВКЛЮЧЁННЫМ трейсингом отдаёт наружу тот же `ValueError`. Пришёл `RuntimeError: generator didn't stop after throw()` — значит `yield` тела оказался внутри `except` (см. `_quiet_span` в шаблоне), ошибка потеряна, чинить до сдачи |
| Свой MLflow-сервер на проект не поднимать | в compose-файлах проекта нет сервиса mlflow (`grep -i mlflow docker-compose*.yml` → только env-переменные); общий сервер — один на компанию |

## 6. Процесс (шаги)

1. Проверь входные артефакты (п.2) и версию скилла в реестре (п.10).
2. Выясни адрес сервера по порядку из п.2. Адреса нет — сообщи пользователю,
   у кого его запросить ([@sanchezgl](https://t.me/sanchezgl) /
   [@KirillBorovkov](https://t.me/KirillBorovkov)), и продолжай с пустой
   переменной.
3. Добавь `mlflow` в зависимости бэкенда; сверь API по докам (п.4).
4. Скопируй [assets/tracing.py](assets/tracing.py) в
   `backend/infrastructure/tracing.py`, адаптируй имя сервиса; вызови
   `setup_tracing()` один раз при старте приложения (lifespan/main) —
   до первого запуска агентов.
5. **Расставь спаны так, чтобы запуск был одним трейсом**: `run_span()` в точке
   входа многошаговой работы (функция прогона конвейера, обработчик запроса),
   `step_span()` вокруг каждого шага внутри. Пропустишь корневой — получишь по
   трейсу на шаг и потеряешь структуру. **Заполни `inputs` корневого спана и
   его выход** — иначе список трейсов будет из пустых строк, а починить это
   задним числом нельзя. У спанов шагов так же заполни вход (системный промпт,
   что подали шагу) и выход (ответ модели, токены) — и **не** передавай промпт
   через `Agent(system_prompt=…)`: это ломает экспорт главного трейса (п.4).
6. Привяжи session/user к трейсам (`tag_current_trace()`) там, где сервис
   их знает.
7. Пропиши `MLFLOW_TRACKING_URI` (и при необходимости `MLFLOW_EXPERIMENT`)

## 8. Логирование и аудит

Append-only запись в `EVIDENCE.md` (проверяемые формулировки):

- дата; файлы созданы/изменены; версии mlflow и pydantic-ai;
- трейсов на один запуск — **1** (а не по одному на шаг); в дереве видно
  последовательность и параллельные шаги;
- в списке трейсов у строки заполнены превью запроса и ответа (это проверка
  того, что корневой спан несёт вход и выход, а не пустой);
- спаны агентов названы осмысленно (`invoke_agent <шаг>`, а не `invoke_agent agent`);
- у спанов шагов заполнены Inputs (системный промпт, вход) и Outputs (ответ,
  токены) — по ним разбирают, ПОЧЕМУ шаг ответил именно так;
- у ВСЕХ трейсов запуска (включая фоновые задачи) сессия равна id запуска —
  проверяется одним запросом: трейсов с чужой/пустой сессией должно быть 0;
- каким режимом включился трейсинг (`pydantic_ai` / `pydantic_ai_otel` /
  `openai`) — строка в логе старта; спаны шага и агента в ОДНОМ трейсе;
- падающий шаг с включённым трейсингом отдаёт наружу свою ошибку, а не
  `RuntimeError` от контекст-менеджера (гейт п.5);
- прогон с пустым `MLFLOW_TRACKING_URI` — приложение стартует, агент
  отвечает;
- прогон с сервером (общим или локальным) — ссылка/скрин трейса, что в нём
  видно (промпт, LLM, tools/MCP);
- grep-гейты п.5 — 0 находок;
- адрес общего сервера: вписан / запрошен у ответственных (у кого, когда);
- отметка о проверке версии скилла (п.10).

## 10. Авто-обновление

`update_check: per_session` — при первом использовании скилла в сессии
сверь локальную `version` с реестром `registry_url`:

| Разница версий | Действие |
|---|---|
| Совпадает | работать дальше молча |
| Патч/минорная | подтянуть автоматически + одна строка уведомления |
| Мажорная | не обновлять, спросить подтверждение — возможны ломающие изменения |
| Реестр недоступен | работать на локальной версии, отметить в `EVIDENCE.md` |
