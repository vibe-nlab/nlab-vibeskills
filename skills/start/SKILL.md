# Start: старт проекта по Golden Path NeuroLab

## 1. Назначение (Purpose)

Превращает свободный запрос пользователя («хочу сервис, который…») в
зафиксированное намерение и готовый к работе каркас проекта: `intent.md` с
проверяемыми критериями приёмки, `spec/SPEC.md` — спецификацию, которая дальше
ведётся как источник правды для кода, — обязательные структурные файлы,
дефолтный стек компании и подтверждённые доступы. Это первый скилл Golden Path —
`Discovery → Design → Prep → Deploy`; без его выхода остальные скиллы
работать не должны.

Скилл — исполняемая форма двух документов реестра:
[`AGENTS.md`](assets/AGENTS.md) (процесс) и
[`project_setup_best_practices.md`](references/project_setup_best_practices.md)
(стек и модели). **Читай их с диска в начале работы, не пересказывай по
памяти** — источник правил один, копий в скилле нет.

Все пути ниже — относительно каталога этого скилла:

```
SKILL_DIR = ${CLAUDE_PLUGIN_ROOT}/skills/start
├── assets/AGENTS.md                              # копируется в проект и адаптируется
├── assets/SPEC.template.md                       # копируется в проект как spec/SPEC.md
├── assets/frontend-next-14-starter/              # копируется в <проект>/frontend
└── references/project_setup_best_practices.md    # только чтение, в проект не копируется
```

## 2. Входные артефакты (Inputs) — ОБЯЗАТЕЛЬНО

Скилл — точка входа, поэтому входов от других скиллов у него нет. Но есть
входы **от человека**, без которых работа не начинается: их нельзя
«додумать», их нужно получить в диалоге и явно зафиксировать.

| Артефакт | Обязателен? | Кто предоставляет | Что делать, если отсутствует |
|---|---|---|---|
| Запрос пользователя (свободная форма) | да | пользователь | нечего фиксировать — спросить, что за проект |
| Проверяемый критерий успеха (хотя бы один, измеримый) | да | пользователь, при помощи вопросов агента | не переходить к п.6 шаг 5 и дальше; если пользователь не может сформулировать — предложить формулировку и получить подтверждение, зафиксировать как **предположение**, а не факт |
| Явные границы задачи (что НЕ входит) | да | пользователь | спросить прямо; пустой раздел в `intent.md` недопустим |
| URL выданного git-репозитория | да — **только к моменту первого push** | ответственные ([@sanchezgl](https://t.me/sanchezgl) / [@KirillBorovkov](https://t.me/KirillBorovkov)) | локальную работу продолжать, push **не делать**, свой репозиторий **не создавать**; попросить пользователя запросить репо и передать свой GitHub-никнейм |
| Ключ LLM (OpenRouter или гейт nlab) | да — только если проект вызывает LLM | пользователь / ответственные | каркас доделать, но не писать LLM-код на «заглушках-обходах»; остановиться и попросить запросить ключ |
| `assets/AGENTS.md` и `references/project_setup_best_practices.md` из `$SKILL_DIR` | да | плагин `nlab` | если файлы недоступны — работать по локальной копии в реестре, отметить в `EVIDENCE.md`, что источник правил не подтверждён |

## 3. Выходные артефакты (Outputs) — ОБЯЗАТЕЛЬНО

| Артефакт | Обязателен? | Формат | Кто читает дальше |
|---|---|---|---|
| `intent.md` | да | markdown: гипотеза результата, критерии приёмки, границы (что НЕ входит), предположения | Design, Prep, ревьюер-человек |
| `spec/SPEC.md` | да | markdown по `$SKILL_DIR/assets/SPEC.template.md`: назначение и критерии, схемы вход/выход, инструменты, схема агентов, границы автономии, зависимости, журнал изменений | Design, Prep, все субагенты-исполнители |
| `AGENTS.md` | да | markdown: копия правил реестра + проектная специфика (стек, домен, ограничения) | любой агент/сотрудник, открывший проект |
| `NOTES.md` | да | append-only журнал: дата, этап, решение, обоснование | все последующие скиллы |
| `feature-list.json` | да | JSON-массив подзадач: `id`, `title`, `acceptance`, `status`, `depends_on` | Design/Prep, декомпозиция на субагентов |
| `EVIDENCE.md` | да | append-only: что проверено и как (проверяемые формулировки) | Prep, Deploy (без него Deploy не стартует) |
| `.gitignore` | да | содержит `.env`, `.env.*` (кроме `*.example`), `servers.md` | git |
| `.env.example` | да, если проект использует env | ключи с `CHANGE_ME`-значениями, без секретов | Prep, Deploy |
| `frontend/` из темплейта компании | да, если у проекта есть UI | копия `$SKILL_DIR/assets/frontend-next-14-starter/` | Design (UI), Prep |
| Локальный git-репозиторий + первый коммит | да | git | аудит, Prep, Deploy |

Все выходные артефакты коммитятся в git по завершении работы скилла.
Коммит-мессадж: что создано и на основании какого входа (запрос
пользователя → `intent.md` → каркас).

## 4. Guidance — рекомендации (можно проигнорировать без тех. последствий)

Дефолты компании из `project_setup_best_practices.md`. Отклонение — только
явным решением пользователя с записью в `NOTES.md`.

- **Спецификация раньше кода — и это документ, а не намерение.** Проект
  ведёт `spec/SPEC.md` (шаблон — `$SKILL_DIR/assets/SPEC.template.md`).
  До кода в нём фиксируются: назначение и критерии приёмки, типизированные
  схемы входа/выхода (pydantic), список инструментов и их контракты, для
  мультиагентных систем — схема агентов (кто кого вызывает, где человек в
  контуре), границы автономии, внешние зависимости.
- **`spec/SPEC.md` — источник правды, и его надо вести.** Код, разошедшийся со
  спецификацией, — ошибка кода, а не повод молча поправить документ.
  Меняется публичный контракт (модель, эндпоинт, инструмент, схема
  агентов) — сначала правится `spec/SPEC.md`, потом код, обе правки уходят
  **одним коммитом**. Каждое изменение контракта добавляет строку в журнал
  изменений спецификации; старые записи не переписываются. Субагентам на
  реализацию передаётся ссылка на раздел `spec/SPEC.md`, а не пересказ задачи.
- **Разделение по этапам.** `/nlab:start` создаёт `spec/SPEC.md` и заполняет
  то, что уже известно из Discovery (назначение, критерии, границы,
  автономия, зависимости). Разделы, требующие проектирования — схемы
  вход/выход, контракты инструментов, схема агентов, — помечаются
  `TODO (этап Design)` и закрываются на этапе Design. Выдумывать их на
  Discovery не нужно: пустой честный `TODO` лучше, чем правдоподобная
  спецификация, которую никто не проектировал.
- **Фронтенд — React из темплейта компании**
  `$SKILL_DIR/assets/frontend-next-14-starter/` (Next.js 14
  pages router + React 18, Tailwind 4, zustand, recharts, готовый
  Dockerfile). Не начинать фронт с нуля и не менять фреймворк. Структуру
  папок темплейта сохранять (`components/`, `hooks/`, `contexts/`,
  `utils/`, `constants/`, `styles/`), версии базового стека «заодно» не
  поднимать. Если проект идёт по дизайн-конвенциям NeuroLab — приоритет у
  скилла `/nlab:design-ui`.
- **Агенты — на pydantic-ai.** Документацию брать из
  <https://ai.pydantic.dev/llms.txt> и ходить по нужным страницам, а не
  писать API по памяти. Схемы входа/выхода — pydantic-модели, инструменты —
  типизированные tools.
- **Модели в Claude Code.** Проектирование, декомпозиция и ревью — основная
  сессия на Fable-5/Opus-5. Задачи кода — субагенты на Sonnet-5. Основная
  сессия проверяет их результат сама (диффы, тесты, линтер) и доводит
  правками; проектные решения субагентам не делегируются. Декомпозиция на
  субагентов идёт по `feature-list.json`: одна подзадача — один субагент с
  контрактом вход/выход.
- **Remix-first, write-second.** Перед тем как писать новую спецификацию,
  скилл или паттерн — проверить реестр: возможно, нужное уже есть.

### Как разговаривать с пользователем

Считай по умолчанию, что перед тобой **не инженер**. Процесс от этого не
упрощается, но объясняется. Это правило действует на всю сессию, а не
только на реплики самого скилла: если работу ведёт основная сессия с
субагентами, отчитывается перед человеком именно она, и отчитывается так же.

- **Сначала смысл, потом детали.** Не начинай ответ со списка путей,
  диффов и команд. Первая фраза — что сделано и что это даёт человеку.
  Технические детали ниже, для тех, кому надо.
- **Термин при первом употреблении — одна поясняющая фраза или замена
  бытовым словом.** «Спецификация — документ, где записано, что именно
  система должна делать; по нему потом пишется код». Не «SDD-артефакт».
  Так же с DDD, pydantic, bounded context, healthcheck, компоузом.
- **Каждый шаг закрывай тремя вещами**: что сейчас сделано, зачем это
  нужно, что дальше. Если чего-то ждёшь от человека — четвёртым пунктом,
  отдельно и конкретно.
- **Блокер — это действие человека, а не состояние системы.** Не
  «репозиторий не выдан, push отложен», а «напишите @sanchezgl в телеграм,
  попросите репозиторий под проект и передайте свой ник на GitHub — без
  этого код останется только у вас на компьютере».
- **Не проси решать то, что решить должен ты.** Вопрос пользователю
  уместен, когда от ответа зависит результат (что считать успехом, что не
  входит в задачу, как называется проект). Выбор библиотеки, раскладки
  папок и формата логов — твоя работа, а не его.
- **Вопросы — по одному смыслу за раз**, с вариантами и рекомендацией.
  «Как поймём, что работает?» лучше, чем «сформулируйте критерии приёмки в
  измеримом виде».
- **В конце — короткое резюме и ровно один следующий шаг.** Не список из
  восьми возможностей: человек не знает, какая из них важная.
- **Не выдавай незаконченное за готовое.** Если раздел спецификации
  помечен `TODO (этап Design)` — так и скажи: «это спроектируем на
  следующем шаге», а не «спецификация готова».

## 5. Enforcement — обязательные правила (нарушение = блокировка)

| Правило | Технический механизм принуждения | Когда |
|---|---|---|
| Агент не создаёт git-репозиторий сам | `gh repo create`, `git remote add` на произвольный URL и «временные» ремоуты запрещены. `git remote -v` должен вернуть URL, зафиксированный в `NOTES.md` как выданный. Ремоут отсутствует или не совпадает → push не выполняется, работа продолжается локально | перед первым push |
| Секреты и ключи не попадают в git | `.gitignore` с `.env`, `.env.*` (кроме `*.example`), `servers.md` — до первого коммита. Плюс скан индекса (проверка **A** ниже): совпадение → коммит не делается, пока значение не вынесено в env | перед каждым коммитом |
| LLM вызывается только через OpenAI-совместимый API, не через CLI | Запуск `claude` и других CLI-агентов как subprocess из кода продукта запрещён. Скан исходников (проверка **B**): совпадение → передача на следующий этап блокируется до устранения | перед handoff |
| `BASE_URL` и ключ LLM — только из env | В коде не должно быть литералов `https://openrouter.ai/api/v1` и `https://ai.nlabstudio.ru/v1` — только `os.getenv("LLM_BASE_URL")`. Скан (проверка **C**): совпадения допустимы лишь в `.env.example` и документации | перед handoff |
| Аудит append-only | `NOTES.md` и `EVIDENCE.md` только дополняются. Проверка **D**: число удалённых строк должно быть `0`, иначе коммит не делается | перед каждым коммитом |
| `spec/SPEC.md` существует и в нём нет пустых обязательных разделов | Проверка **E**: все восемь заголовков шаблона на месте. Отсутствует раздел → `spec/SPEC.md` не считается созданным, handoff не отдаётся | перед handoff |
| Код не уезжает вперёд спецификации | Проверка **F**: если в индексе есть изменения кода, меняющие публичный контракт (модели, эндпоинты, объявления инструментов), в том же индексе должен быть и `spec/SPEC.md`. Нет — коммит не делается, пока спецификация не обновлена | перед каждым коммитом с кодом |
| Prep не стартует с недопроектированной спецификацией | Проверка **G**: в `spec/SPEC.md` не осталось `TODO`. Есть — передача на Prep блокируется (для `/nlab:start` это нормальное состояние: `TODO (этап Design)` закрывает этап Design, а не Discovery) | перед передачей на Prep |
| Нет проверяемого критерия приёмки — нет перехода дальше | Раздел «Критерии приёмки» в `intent.md` не может быть пустым или состоять из неизмеримых формулировок («работает хорошо»). Пустой/неизмеримый раздел → скилл останавливается и не отдаёт handoff | перед handoff |
| Discovery не пропускается по просьбе пользователя | Просьба «просто напиши код» не отменяет `intent.md`. Минимально допустимый объём — одна фраза-гипотеза + один критерий успеха; ноль — недопустим. Отклонение фиксируется в `NOTES.md` | всегда |

Команды проверок — выполнять как есть, результат каждой записывать в
`EVIDENCE.md` (п.8):

```bash
# A. Секреты в индексе. Ожидание: пусто. Есть вывод → не коммитить.
git diff --cached | grep -nE '(sk-[A-Za-z0-9]{16,}|gh[pous]_[A-Za-z0-9]{20,}|(API_KEY|TOKEN|SECRET|PASSWORD)=[^C[:space:]][^[:space:]]{7,})'

# B. Вызов LLM через CLI из кода продукта. Ожидание: пусто.
grep -rnE -A2 '(subprocess|Popen|os\.system|child_process|execSync|spawn)' \
  --include='*.py' --include='*.js' --include='*.ts' . \
  | grep -iE 'claude|codex|gemini|copilot'

# C. Захардкоженный BASE_URL. Ожидание: пусто (в .env.example — допустимо).
grep -rn 'openrouter.ai\|ai.nlabstudio.ru' \
  --include='*.py' --include='*.js' --include='*.ts' .

# D. Append-only аудит. Формат вывода: <добавлено> <удалено> <файл>.
# Ожидание: вторая колонка = 0 для обоих файлов.
git diff --cached --numstat -- NOTES.md EVIDENCE.md

# E. Обязательные разделы spec/SPEC.md на месте. Ожидание: пусто.
for h in "1. Назначение" "2. Схемы" "3. Инструменты" "4. Схема агентов" \
         "5. Границы автономии" "6. Данные" "7. Что явно НЕ входит" \
         "8. Открытые вопросы"; do
  grep -q "^## $h" spec/SPEC.md || echo "нет раздела: $h"
done

# F. Публичный контракт изменён без правки spec/SPEC.md. Ожидание: пусто.
if git diff --cached -U0 -- '*.py' '*.ts' '*.js' '*.tsx' | grep '^+' \
     | grep -qE '(class .*\(BaseModel\)|@(app|router)\.(get|post|put|delete|patch)|@agent\.tool|def .*-> *[A-Z])'
then
  git diff --cached --name-only | grep -qx 'spec/SPEC.md' \
    || echo "контракт изменён, а spec/SPEC.md не в коммите"
fi

# G. Спецификация допроектирована. Ожидание: пусто.
# Для /nlab:start остаток TODO (этап Design) — норма, проверка нужна перед Prep.
# Строки-цитаты (`>`) исключены: пояснение в шапке шаблона само упоминает TODO.
grep -rn 'TODO' spec/ --include='*.md' | grep -vE '^[^:]+:[0-9]+:[[:space:]]*>'
```

`grep` возвращает код 1, когда совпадений нет — для проверок A–C это и есть
успех. Не трактуй ненулевой код возврата как сбой проверки.

Если непонятно, guidance это или enforcement — считать enforcement и
остановиться до подтверждения человека.

## 6. Процесс (шаги)

1. **Прочитать правила с диска**: `$SKILL_DIR/assets/AGENTS.md` и
   `$SKILL_DIR/references/project_setup_best_practices.md`. Один раз за
   сессию сверить версию скилла с реестром (п.10).
2. **Понять, что за проект.** Задать пользователю ровно то, чего не хватает
   для `intent.md`: что должно получиться, как проверить, что НЕ входит.
   Не задавать вопросов о деталях, которые разрешено решать самому (п.7).
3. **Определить тип проекта** — сервис / агент или мультиагентная система /
   фронтенд / комбинация. От этого зависят шаги 7–9 и состав стека.
4. **Проверить доступы**: выдан ли git-репозиторий (URL); нужен ли проекту
   LLM и есть ли ключ (OpenRouter или гейт nlab). Чего нет — не изобретать
   обход, а зафиксировать как блокер в `intent.md` и сказать пользователю,
   что и у кого запросить (п.2).
5. **Написать `intent.md`**: гипотеза результата, измеримые критерии
   приёмки, границы задачи, предположения (помеченные как предположения),
   блокеры из шага 4. Пустых разделов быть не должно.
6. **Развернуть каркас**: `AGENTS.md` (правила реестра + проектная
   специфика: домен, стек, ограничения), `NOTES.md` (первая запись — дата,
   этап Discovery, принятые решения и почему), `feature-list.json`
   (декомпозиция критериев приёмки в подзадачи с `acceptance` у каждой),
   `EVIDENCE.md` (первая запись — что проверено на этом шаге), `.gitignore`,
   `.env.example` при необходимости.
7. **Создать `spec/SPEC.md`**: скопировать `$SKILL_DIR/assets/SPEC.template.md`
   в проект как `spec/SPEC.md` (папка `spec/` — этап Design добавит в неё
   `schemas.md`, `tools.md`, `agents.md`) и заполнить из Discovery — назначение,
   критерии приёмки (перенести из `intent.md` без переформулирования, с
   привязкой к `id` подзадач `feature-list.json`), границы автономии,
   внешние зависимости и их поведение при отказе, что явно не входит,
   открытые вопросы. Разделы «Схемы входа и выхода», «Инструменты» и
   «Схема агентов» оставить с `TODO (этап Design)` — кроме случая, когда
   контракт уже однозначно следует из Discovery. Для не-мультиагентного
   проекта в разделе «Схема агентов» написать «не применимо», раздел не
   удалять. Заполнить шапку (статус `draft`, коммит `intent.md`, дата) и
   первую строку журнала изменений.
8. **Зафиксировать стек** по п.4 и записать выбор в `NOTES.md` с
   обоснованием. Любое отклонение от дефолта компании — отдельной строкой с
   пометкой, что это решение пользователя.
9. **Развернуть фронт**, если у проекта есть UI: скопировать
   `$SKILL_DIR/assets/frontend-next-14-starter/` в
   `<проект>/frontend`, заменить `name` в `package.json` на имя проекта,
   выполнить `npm install` и убедиться, что `npm run dev` поднимается.
10. **Прогнать enforcement-проверки** из п.5 (A–F: секрет-скан, скан
    CLI-вызовов LLM, захардкоженный `BASE_URL`, append-only, разделы
    `spec/SPEC.md`, контракт без правки спецификации) и записать результат
    каждой в `EVIDENCE.md` проверяемой формулировкой. Проверка **G** здесь
    не применяется — остаток `TODO (этап Design)` на Discovery штатен.
11. **`git init` (если репозитория ещё нет) и первый коммит.** Push — только
    в выданный репозиторий и только после проверки `git remote -v`. Нет
    выданного репо → коммит локальный, push отложен, причина записана в
    `NOTES.md`.
12. **Отдать handoff** (п.9) — человеческим языком по правилам п.4:
    что теперь есть у проекта и что это даёт, что осталось спроектировать
    на следующем шаге, какие блокеры и что по каждому сделать человеку,
    и один конкретный следующий шаг. Список файлов — после этого, а не
    вместо этого.

## 7. Уровень автономии и обоснование

`autonomy_level: R4` для основной части — Discovery и локальные файлы
полностью обратимы. По шагам уровень разный:

| Шаг | Обратимость | Уровень | Что это значит |
|---|---|---|---|
| Вопросы, `intent.md`, `spec/SPEC.md`, каркас, `feature-list.json` | полностью обратимо | R4 | действовать самостоятельно, не переспрашивать по мелочам |
| Копирование темплейта фронта, `npm install` | обратимо (локально) | R4 | самостоятельно |
| Выбор стека с отклонением от дефолта компании | обратимо, но влияет на весь проект | R2 | только по явному решению пользователя + запись в `NOTES.md` |
| Первый push в выданный репозиторий | труднообратимо (общая история) | R2 | подтверждение remote по `git remote -v` + согласие пользователя |
| Создание git-репозитория | необратимо в части владения/доступов | **R0 — запрещено** | делает только человек через ответственных |

Правило по умолчанию: сомневаешься в обратимости — считай, что действие
необратимо, и спроси.

## 8. Логирование и аудит

В `EVIDENCE.md` по завершении скилла должны быть проверяемые записи, а не
оценки. Обязательный минимум:

- `intent.md` создан; критериев приёмки — N, из них измеримых — N (перечислить);
- `spec/SPEC.md` создан из шаблона; проверка **E** — все 8 разделов на месте;
  что заполнено из Discovery; сколько осталось `TODO (этап Design)` и в каких
  разделах; проверка **F** — результат;
- каркас: какие файлы созданы (список путей), какие уже существовали и не тронуты;
- секрет-скан индекса выполнен, команда и результат («0 совпадений» или что найдено и куда вынесено);
- скан CLI-вызовов LLM выполнен, команда и результат;
- проверка append-only (`git diff --cached --numstat -- NOTES.md EVIDENCE.md`) — удалённых строк 0;
- фронт (если разворачивался): `npm install` — код возврата, `npm run dev` — поднялся на порту N;
- доступы: репозиторий выдан (URL) / не выдан — блокер; ключ LLM есть / запрошен у ответственных;
- проверка версии скилла в реестре: выполнена (совпадает / расхождение) или не выполнена и почему.

В `NOTES.md` — решения и их обоснование: тип проекта, выбранный стек,
каждое отклонение от дефолта компании с пометкой «решение пользователя»,
URL выданного репозитория при получении.

## 9. Передача следующему скиллу (Handoff)

Передаётся этапу **Design** Golden Path. Обязательно на выходе: `intent.md`
с непустыми критериями приёмки и границами, `spec/SPEC.md` со всеми разделами
(незакрытые помечены `TODO (этап Design)`), `feature-list.json`,
инициализированные `AGENTS.md` / `NOTES.md` / `EVIDENCE.md`, всё
закоммичено.

Этап Design (`/nlab:design`) работает **в этом же `spec/SPEC.md`**, а не заводит свой документ:
закрывает `TODO`, дописывает схемы вход/выход, контракты инструментов и
схему агентов, меняет статус в шапке `draft → design`, добавляет строку в
журнал изменений. Prep не стартует, пока проверка **G** не пуста.

Дальше по цепочке, в зависимости от проекта:

| Что дальше | Кто делает |
|---|---|
| Архитектура и спецификация (SDD + DDD), схема агентов | скилл `/nlab:design` |
| UI по дизайн-системе NeuroLab | скилл `/nlab:design-ui` |
| Подготовка репозитория к деплою | скилл `/nlab:dokploy-prep` |
| Деплой | скилл `/nlab:dokploy` |

Если остались блокеры из п.6 шага 4 (нет репозитория, нет ключа LLM) —
передавать дальше можно, но блокер обязан быть виден в `intent.md` и
озвучен пользователю; Deploy с незакрытым блокером не стартует.

## 10. Авто-обновление

`update_check: per_session` — один раз при первом использовании скилла в
сессии сверить `version` с `registry_url`.

| Разница версий | Действие |
|---|---|
| Совпадает | Работать дальше молча |
| Патч/минорная | Сообщить одной строкой и предложить `/plugin marketplace update nlab-vibeskills` |
| Мажорная | Не работать по новым правилам без подтверждения — сообщить о ломающих изменениях и спросить |
| Реестр недоступен | Работать на локальной версии, отметить в `EVIDENCE.md`: «проверка обновления не выполнена» |

Обновление плагина выполняет пользователь: Claude Code не даёт агенту
обновлять плагины самостоятельно. Это guidance-механизм — недоступность
реестра не блокирует работу скилла.

## 11. Примеры

**Вход** (реплика пользователя):

> Нужен сервис, который принимает договоры в PDF и вытаскивает оттуда
> стороны, сумму и срок. Хочу веб-интерфейс, чтобы загружать файл и видеть
> результат.

**Диалог скилла** (только недостающее): как поймём, что работает — сколько
договоров и с какой точностью? Что НЕ входит — редактирование договоров,
подписание, хранение дольше сессии? Репозиторий выдан? Ключ LLM есть?

**Выход** — `intent.md`:

```markdown
# Intent: экстрактор реквизитов договора

## Гипотеза результата
Веб-сервис: пользователь загружает PDF договора и получает стороны, сумму
и срок в структурированном виде.

## Критерии приёмки
1. На контрольной выборке из 20 договоров все три поля извлечены верно
   минимум в 17 случаях (85%).
2. Ответ на договор до 20 страниц — не дольше 30 секунд.
3. PDF без текстового слоя — явная ошибка пользователю, не пустой результат.

## Границы (НЕ входит)
- редактирование и подписание договоров;
- хранение файлов дольше пользовательской сессии;
- типы документов, кроме договоров.

## Предположения
- Договоры на русском языке (подтверждено пользователем).
- Максимальный размер файла 10 МБ (предположение агента, не подтверждено).

## Блокеры
- Репозиторий не выдан — push отложен, запросить у @sanchezgl / @KirillBorovkov.
```

**Выход** — `spec/SPEC.md` (фрагмент; показано, что заполняется на Discovery, а
что остаётся этапу Design):

```markdown

- **Статус:** draft

## 2. Схемы входа и выхода
```
